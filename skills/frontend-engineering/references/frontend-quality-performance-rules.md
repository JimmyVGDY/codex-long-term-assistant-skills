# 前端质量、性能与交付规则

## 一、性能与资源

检查重复渲染、深比较、大对象复制、主线程长任务、同步布局、布局抖动、大列表、图片视频、Canvas、编辑器、预览资源、Detached DOM、监听器、Object URL、缓存增长、重复请求、预取过度和第三方脚本。

评估路由分包、按需加载、Tree Shaking、Bundle 重复依赖、压缩、图片格式、字体和缓存。Web Worker、虚拟列表、Memo、缓存和预加载必须基于真实瓶颈，不为简单逻辑增加复杂度。

性能结论优先使用构建分析、Core Web Vitals、RUM、浏览器 Performance/Memory、Lighthouse 或可复现对比，不凭代码感觉宣称优化显著。

## 二、样式、可访问性和国际化

检查响应式、触控、缩放、高 DPI、暗色、打印、CSS 作用域、层叠冲突和布局溢出。检查语义 HTML、键盘、焦点、ARIA、对比度、屏幕阅读器和动态内容通知。

国际化检查文本扩展、复数、RTL、数字/金额/日期、时区、夏令时和服务端/客户端格式一致性。不能只凭单张截图判定通过。

## 三、构建、环境和发布

- 区分构建时与运行时变量；
- 检查 API Base URL、代理、Base Path、History 回退、内容哈希、CDN、缓存头和 Source Map；
- 检查开发服务器与生产构建差异、Workspace/Monorepo 构建缓存和共享包版本；
- 灰度期间验证新旧前端、后端接口、Service Worker 和静态资源兼容；
- 不无理由修改全局 npm 配置、包管理器、锁文件或大版本依赖。

## 四、测试与最低验证

修改前端运行行为后，至少执行项目实际正式生产构建。按范围选择：

- TypeScript 类型检查与项目 Lint；
- 单元和组件测试；
- 路由、状态、表单和 API 契约测试；
- Playwright/Cypress E2E 与目标浏览器；
- 视觉回归、响应式、键盘和可访问性验证；
- SSR/Hydration、SSE/WebSocket、文件、权限、缓存和离线场景；
- Bundle、Core Web Vitals 和内存基线。

至少验证正常、加载、空、错误、禁用、重复点击、刷新、路由切换、权限不足、接口超时/失败和异步竞态。构建通过不等于交互正常，全部 Mock 的单测不等于集成验证，静态检查不能冒充浏览器运行验证。

## 五、代码审查输出

审查结论至少覆盖：框架与版本识别、组件和状态、请求竞态、权限与安全、SSR/实时连接、资源释放、表单列表文件、性能、可访问性、构建测试证据、新旧版本兼容和未验证项。
## 六、设计系统、SEO 与浏览器兼容

设计系统和组件库需检查 Design Token、主题、CSS 变量、组件公开契约、版本兼容、样式隔离、按需加载和消费者迁移。不得为了统一外观破坏可访问性、业务语义或历史页面兼容。

面向公开 Web 的页面还应按需检查：Title/Meta、Canonical、Robots、Sitemap、Open Graph、结构化数据、语义 HTML、SSR/SSG 可抓取性、重定向和错误状态。SEO 结论应基于构建产物、实际响应和抓取验证，不只看组件源码。

浏览器兼容应以项目 `browserslist`、企业终端、WebView/设备版本和真实统计为准，检查 Polyfill、CSS 特性、模块格式、Intl、文件/媒体 API 和降级路径。不得把本机最新版 Chromium 通过表述为所有目标浏览器通过。
