# Logs、Metrics、Trace、Profile、告警与变更事件

## 四、可观测性证据源模型

### 4.1 日志

用于确认离散事件、异常链、业务状态、重试和恢复。必须考虑采样、轮转、异步写入、日志级别误用和日志注入。

### 4.2 Metrics 指标

至少区分：

- 流量：请求量、任务量、消息生产和消费速率；
- 错误：错误率、失败类型、超时、重试和降级；
- 延迟：平均、P50、P95、P99 和长尾；
- 饱和度：CPU、内存、GC、线程、连接池、队列、磁盘、网络和 GPU；
- 业务指标：成功率、状态分布、积压和完成时长。

指标分析必须记录聚合周期、标签过滤、缺失值、采样和基数。不得把平均值替代长尾，不得把聚合后相关性直接写成单请求因果。

### 4.3 分布式 Trace

检查：

- Root Span、关键路径和最慢 Span；
- 上下游父子关系、异步边界和跨线程上下文；
- 重试造成的重复 Span；
- 采样策略、缺失 Span 和时钟偏移；
- HTTP、数据库、Redis、MQ、文件和模型调用耗时；
- 错误状态、超时和取消传播。

Trace 只能代表被采样请求。不能因未采到异常 Trace 就断言所有请求正常。

### 4.4 Profiling 与转储

已有 JFR、Heap Dump、Thread Dump、GC 日志、py-spy、cProfile、火焰图或 GPU Profile 时，可以只读分析。在线重新采集属于独立操作授权，生产环境必须限制持续时间、采样频率、输出大小和停止条件。

重点检查：

- CPU 热点、锁竞争和线程阻塞；
- 堆内、堆外、对象保留和内存增长；
- GC 暂停、分配速率和大对象；
- Python Event Loop 阻塞、GIL 和多进程；
- GPU 显存、Kernel、数据搬运和等待；
- Profile 与同时间窗日志、指标和 Trace 是否一致。

### 4.5 告警与变更事件

关联：

- 监控告警触发、恢复和抑制；
- 发布、回滚、配置刷新、扩缩容和流量切换；
- 数据库 DDL、索引、依赖版本和基础设施变化；
- 定时任务、批处理、业务活动和外部依赖故障。

告警不是根因，发布后出现故障也不自动证明发布是根因。

### 4.6 多证据源关联

按统一时区建立：

```text
变更事件 → 指标异常 → Trace 关键路径 → 日志/堆栈 → Profile 资源证据 → 恢复事件
```

每个结论至少记录支持证据、反证、缺口和证据等级。单一证据源不足时必须明确保留未验证项。
