# 实施后审查、归并、集中修复与定向复核

## 一、启动前置条件

第一轮前必须确认：功能边界已完成；最低定向验证已执行或阻塞已记录；差异稳定；基线、HEAD 和改动范围明确；隔离等级与预算已记录；审查包已生成且 freshness 检查通过。

如果工作区在生成 packet 后变化，旧 packet 和对应结果必须标记为 stale，不得继续派发。

## 二、统一审查包与渐进读取

使用 `review_packet.py create` 生成：

- `packet-manifest.json`：基线、HEAD、范围、文件和证据索引；
- `packet-summary.md`：任务与验证最小摘要；
- `diff-stat.txt`、`name-status.txt`：低成本范围判断；
- `diff.patch`：需要时再读取的完整差异。

Reviewer 读取顺序：摘要和统计 -> 分配范围的 hunk -> 改动文件完整上下文与直接依赖 -> 证据不足时才扩大。禁止每个 Reviewer 从头扫描整个仓库，也禁止把完整父会话、原始日志和完整工具输出复制进审查包。

## 三、第一轮并行审查

每个 Reviewer 必须获得唯一职责、文件/调用链范围、排除范围、packet hash、轮次/深度、证据要求、模型档位、输出 Schema 和隔离等级。

主协调 Agent 等待当前轮计划中的 Reviewer 返回后统一归并；不因一个 Reviewer 先返回问题就边审边改。Reviewer 失败时最多重试一次；相同 Reviewer 对相同 packet 的重复派发必须提供第二意见理由。

优先并行只读、相互独立、读取密集的工作；有状态测试、数据库、中间件、环境操作和共享文档写入不并行交给 Reviewer。

## 四、结果归并

主协调 Agent：

1. 按文件、调用链和业务边界合并；
2. 删除重复发现并将同根因表象合并；
3. 区分已确认、高概率、推测和未验证；
4. 比较冲突证据，能直接裁决时不新增 Agent；
5. 标记是否由本次改动引入；
6. 形成阻塞/高/中/低问题和修复后验证方式；
7. 输出最小完整修复集合与顺序。

同一争议最多追加一个专项第二意见 Reviewer；仍无法确认时保留为未验证，不继续递归派生。

## 五、集中修复与定向复核

Reviewer 不修改代码。主协调 Agent 归并后再由实施 Agent 一次性完成最小完整修复，随后：

- 检查新 diff；
- 只重跑受影响的最低验证；
- 重新生成或刷新审查包；
- 只复核受影响维度，默认不超过 2 个 Reviewer；
- 未改变的证据按指纹复用，不重复执行等价扫描。

公共接口、共享组件、全局序列化、权限拦截器、公共消息模型或数据库公共字段变化时才扩大复核范围。
