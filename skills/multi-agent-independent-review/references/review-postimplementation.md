# 实施后审查、并行归并、集中修复与定向复核

## 本文件目录

- 八、实施后复审前置条件
- 九、第一轮并行审查
- 十、结果归并与根因聚类
- 十、最小完整修复集合

## 八、实施后复审前置条件

开始第一轮前，主协调 Agent 必须确认：

1. 当前功能边界已经完成修改；
2. 与改动直接相关的最低定向验证已经执行，或阻塞原因已记录；
3. `git diff` 已经稳定，不再进行边审边大改；
4. 基线 Commit、当前 HEAD、改动文件和差异范围明确；
5. 已记录 Reviewer TOML 声明与运行时隔离等级；严格任务必须满足 Level A，普通可写父会话只能按 Level B 报告；
6. 已确定风险级别、Reviewer 组合和预算；
7. 如启用长期任务记忆，已写入“复审启动检查点”。

复审启动检查点至少记录：

- 功能边界；
- 基线和差异范围；
- 第一轮 Reviewer 清单；
- 当前深度、轮次和剩余预算；
- 最低验证结果；
- 停止条件。

## 九、第一轮并行审查

### 6.1 派发要求

每个 Reviewer 的任务必须包含：

- 唯一职责；
- 审查文件和调用链范围；
- 不负责的内容；
- 当前轮次和逻辑深度；
- 功能边界和基线；
- 证据要求；
- 输出模板；
- 禁止修改、提交、推送、部署和继续派生；同时声明当前隔离等级，Level B 不得写成系统强制禁止；
- 当前 Reviewer 预算不是其可自行消费的授权。

### 6.2 等待要求

- 主协调 Agent 必须等待本轮适用 Reviewer 全部返回；
- Reviewer 运行期间不得收到一条问题就立即修改代码；
- Reviewer 失败或超时时，记录失败并判断是否重试一次、替换 Reviewer 或标记未验证；
- 不得因为某个 Reviewer 先返回“通过”就提前终止其他维度。

### 6.3 适合并行的工作

优先并行：

- 只读代码和调用链审查；
- 安全、兼容、性能和状态扫描；
- 测试证据检查；
- 文档或框架 API 核验；
- 日志、执行计划和差异分析。

谨慎并行：

- 多 Agent 同时修改同一工作树；
- 多 Agent 同时更新共享外部记忆；
- 多 Agent 同时执行有状态测试；
- 多 Agent 同时操作数据库、中间件和环境。

本复审工作流要求 Reviewer 行为只读，不并行写代码。是否具有系统级写入隔离必须由运行时证据决定。

## 十、结果归并与根因聚类

主协调 Agent 收齐结果后，必须完成：

1. 按文件、调用链和业务边界归并；
2. 删除完全重复的问题；
3. 将同一根因导致的多个表象合并；
4. 区分已确认、高概率、推测和未验证；
5. 对 Reviewer 结论冲突进行证据比较；
6. 标记问题是否由本次改动引入；
7. 按阻塞、高、中、低、建议分级；
8. 区分本次范围内问题和额外发现；
9. 为每个问题定义修复后验证方式；
10. 形成最小完整修复集合和修复顺序。

### 7.1 同根因合并示例

以下表象：

- 消息重试导致重复扣减；
- 消费者无幂等记录；
- 数据库没有唯一约束；
- ACK 早于业务提交；

应聚合为“消息消费幂等与成功边界不完整”，统一评估业务幂等键、唯一约束、事务提交、ACK、重试和并发测试，而不是拆成四次孤立修复。

### 7.2 冲突处理

Reviewer 冲突时：

1. 首先比较实际代码、配置、测试和运行证据；
2. 主协调 Agent 能直接裁决时，不新增 Agent；
3. 仍无法裁决且影响阻塞结论时，可在深度 2 启动一个专项第二意见 Reviewer；
4. 同一争议最多追加一次第二意见；
5. 仍无法确认时标记未验证并保留决策点。

---

## 十、最小完整修复集合

集中修复清单应满足：

- 能完整消除本次范围内的阻塞根因；
- 不把同根因拆成多次反复修改；
- 不顺手处理无关低优先级问题；
- 不改变未要求的公共契约和业务口径；
- 明确每项修改影响的验证和复审维度；
- 明确修复顺序和回滚点。

主协调 Agent 在形成修复集合后，再由实施 Agent统一修改。

禁止：

- Reviewer 直接改代码；
- 多个 Reviewer 同时写同一工作区；
- 为追求“一次修完”扩大到无关重构；
- 为减少轮次忽略新发现的高风险问题。
