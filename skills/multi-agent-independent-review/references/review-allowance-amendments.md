# 复审额度追加与恢复

适用于 Codex Desktop 增强 Plugin 的 `desktop-g6-deterministic-v1`。规划单位是插件配额，不是实际 credits、Token 或费用。主 Agent 与子 Agent 的权限不由额度记录扩大。

## 先检查支持，再请求批准

控制器先比对当前安装状态、安装事务、缓存清单、账户运行库和调用方代码。匹配的读取器安装完成之前，不向旧账本写入新事件。缺少可核验的原生父会话来源，或仍要求未取得的系统隔离时，不提出追加问题。

只使用当前项目与宿主提供的真实聊天、转录和仓库路径。内部管理脚本不构成独立 CLI 产品或新的兼容验收轨道。

```text
review_controller.py init --review-dir <外部目录> --repo-path <仓库> --boundary-id <边界> --host-session-id <真实聊天ID>
review_controller.py bind-native-source --review-dir <外部目录> --transcript-path <真实父会话文件>
review_controller.py plan --review-dir <外部目录> --phase post --packet-dir <当前审查包> --reviewers <角色> --allowed-path <范围>
review_controller.py dispatch --review-dir <外部目录> --phase post --round 1 --reviewer <角色>
```

`--reserve-repair` 仅用于确实必需的后续修复复核。`--review-stage repair_review` 区分修复复核；多个角色仍受默认并发限制。审查包必须属于当前仓库和边界，相关路径必须位于批准范围。

## 一次批准对应一份明确申请

无法派发时先读取 `dispatch_recovery`。单位不足、尝试次数不足、并发占满、原生记录未读完和来源不匹配分别处理。

```text
review_controller.py allowance-quote --review-dir <外部目录> --additional-reviews 1 --retry-limit 2 --locale zh-CN
```

`--additional-reviews` 表示每个选中角色需要可用的追加执行次数。已有未使用分配会抵扣缺口；`--reviewer` 可选定单个角色，`--future-review` 选择已登记的后续复核。返回的总 Reviewer 数、规划单位、尝试上限和角色/档位才是本次申请范围。

执行 `next_action`：仅在要求发问时，将返回的 `question` 和 `options` 原样用于用户输入工具。已有可用批准返回恢复派发，已经呈现的申请继续等待原回复，在途或终态未知则查询原调用。不要重复生成申请，也不要以改名、拆分或新聊天重置预算。

中文与英文固定问题属于同一请求，`--locale en` 只改变呈现，不增加额度。输入语法和既有问题版本保留原字节，英文包不会改写这些协议字符串。

## 原生授权与恢复

只从绑定父会话的原生用户消息读取批准，核验会话、仓库、文件身份、消息身份、时间及对应申请。自动目标上下文、规则注入、引用内容和工具输出不能批准。当前适配要求原生 `user.text` 元数据；无法核验时保持未批准。

```text
review_controller.py allowance-recover --review-dir <外部目录>
review_controller.py allowance-status --review-dir <外部目录>
```

批准记录追加到原账本，独立额度来源绑定工作、角色和档位。并发和重复响应只能产生一次分配；入账后中断可从原消息恢复，不再次索要同一份批准。大记录按有界游标读取，尚未读完时继续恢复，不把缺少结果当作未批准。

恢复后重新 `dispatch` 并执行精确参数。工作身份不随 packet 哈希、短期许可过期或范围内修复变化而重置；材料与完整派发参数仍需重新校验。超出原范围、不同档位和已关闭工作不能消费原分配。

宿主可能以不透明形式传递子任务消息。原生入口通过已登记的任务名、角色、档位和新鲜审查包定位工作，再核验控制器保存的独立审查材料；不把传输字节当作业务明文。材料在扣额前检查，并通过 `SubagentStart` 交给 Reviewer。通过结果必须同时包含匹配的 packet 与 context 摘要，且存在原生上下文交付记录。材料文件属于显式审查输入，生命周期观察仍只保存摘要和引用。

不透明续跑缺少独立派发标识时，返回同一工作下的重新派发步骤，继续使用已有批准。不能通过猜测消息内容、清账或再次索取同一批准来恢复。上述流程仍为逻辑只读，不构成系统文件隔离证明。

## 计账与生命周期

- 基础额度、追加额度和总用量分别展示；预占在同一个根锁下检查并记录唯一额度来源。
- 尚未创建的已证实失败释放规划单位，保留尝试计数；未知结果保留在途占用并恢复原句柄。
- 重试次数、并发、深度、安全与完整性边界继续有效；已通过且材料未变化的复审不重复执行。
- 撤销或关闭只阻止未消费的后续执行，已经创建的调用仍须结算；不得删除历史或补造终态。
- 旧 G6 前缀与原策略摘要不变；新增事件使用 `g6-budget-journal/2`。V3/V4 等历史解释器保持冻结。

## 部署、回滚与验收

先升级读取器并验证安装，再允许写入扩展事件。安装事务未完成时保持未支持。新增事件存在后，不回退到只理解旧格式的读取器；保留账本，停止受影响派发，使用仍能读取扩展事件的修复版本。

必须分别记录：收到回复、额度入账、实际创建、终态与复审结论。隔离子进程测试不证明真实用户批准或模型执行，安装校验也不证明当前聊天已加载并执行 Hook。

平台的 Hook 信任与调用覆盖独立于插件账本；未取得实际拦截与回执时只称策略约束。官方说明也指出部分专用调用路径可能不经过通用 Hook，并且转录格式可能变化。[官方 Hook 说明](https://learn.chatgpt.com/docs/hooks#tool-coverage)
