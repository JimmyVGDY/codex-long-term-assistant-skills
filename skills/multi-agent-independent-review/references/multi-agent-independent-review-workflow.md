# 多 Agent 独立复审与最少有效修复轮次工作流

> 本工作流同时覆盖高风险实施前设计与影响审查，以及真实代码或可执行行为发生变化后的提交前复审。它不能替代构建、运行测试、数据验证或生产验收。

## 一、目标

多 Agent 复审的目标不是无上限增加 Reviewer，而是：

- 在第一轮尽可能完整地发现功能、回归、安全、性能、数据和状态风险；
- 把噪声工作移出主线程，保持主协调 Agent 聚焦目标、授权、决策和最终交付；
- 等待本轮结果收齐后统一去重、归因和分级；
- 将同一根因导致的多个表象合并为一组完整修复；
- 降低“改一处、审一次、再改一处”的多次回炉；
- 对修复后的受影响范围进行定向复核，而不是机械重跑所有 Reviewer。

正式原则：

> **一次发现、统一归因、集中修复、定向复核，追求最少有效修复轮次。**

“最少”不等于隐瞒问题。任何新发现的阻塞问题都必须如实保留和处理。

## 二、默认安全参数

除非项目规则或用户明确设置更严格上限，采用：

```text
MAX_REVIEW_AGENT_DEPTH = 3
MAX_PREIMPLEMENTATION_REVIEW_ROUNDS = 1
MAX_PREIMPLEMENTATION_REVIEWERS = 4
MAX_POST_REVIEW_ROUNDS = 3
MAX_PARALLEL_REVIEWERS = 6
MAX_TOTAL_REVIEW_AGENTS_PER_BOUNDARY = 12
MAX_REPAIR_ROUNDS = 3
```

含义：

- 深度 0：主协调 Agent；
- 深度 1：第一轮专业 Reviewer；
- 深度 2：冲突裁决、证据补足或专项第二意见；
- 深度 3：最终定向复核；
- 深度达到 3 后禁止继续派生 Reviewer；
- 高风险任务在编码前最多自动执行 1 轮实施前审查，使用 2～4 个 Reviewer；
- 实施后同一功能边界最多自动执行 3 轮复审和 3 轮集中修复；
- 同时运行的 Reviewer 默认不超过 6；
- 全部轮次累计 Reviewer 不超过 12。

当前平台、配置、权限或用户要求的上限更低时，采用更低值。不得通过拆成等价工具调用、隐藏子任务或重复命名规避上限。

### 2.1 单一协调者

- 只有主协调 Agent 负责派发 Reviewer、汇总结果、维护预算和决定下一轮；
- Reviewer 在行为规则上不得自行派生子 Reviewer；该约束是否具有系统强制性取决于运行时权限，必须按隔离等级报告；
- 需要补充专家时，Reviewer 只提出“建议追加专项复审”，由主协调 Agent 判断是否在预算内执行；
- 主协调 Agent 是共享复审台账和外部记忆文档的唯一写入者。

## 三、运行时隔离等级与严格复审前置条件

### 3.1 配置声明不等于运行时事实

自定义 Reviewer TOML 中的：

```toml
sandbox_mode = "read-only"
```

只表示配置意图和期望行为。主协调 Agent 必须把以下内容分别记录：

- Reviewer 配置文件和声明值；
- 父会话实际沙箱与权限配置；
- 是否确认运行时真正使用了指定 Agent 类型；
- 子 Agent 可确认的运行时权限；
- 是否做过一次性临时仓库的受控写入探针；
- 最终隔离等级和严格只读资格。

不得把“Reviewer 没有主动写文件”当作“系统阻止 Reviewer 写文件”。

### 3.2 隔离等级

| 等级 | 定义 | 可报告内容 | 适用边界 |
|---|---|---|---|
| Level A：`system-readonly` | 父会话实际为只读，或受控探针明确因沙箱拒绝写入 | 系统隔离复审 | 高风险、生产、权限安全、不可逆操作 |
| Level B：`logical-readonly` | 父会话可写，Reviewer 仅依靠指令不写；写入成功或未形成系统隔离证据 | 逻辑只读复审 | 普通研发复审，必须明确风险 |
| Level C：`self-review` | 实施 Agent 自己检查，没有独立 Reviewer 上下文 | 自查 | 不能替代独立复审 |
| `unknown` | 运行时证据不足 | 未验证 | 不得声称系统只读 |

### 3.3 严格只读要求

以下场景默认要求 Level A：

- 生产环境、真实用户数据或敏感凭据；
- 数据库、Redis、MQ、对象存储等具有写权限的环境；
- 权限、安全、资金、库存、不可逆迁移；
- 用户明确要求“系统强制只读”或“严格只读”；
- Reviewer 运行在高权限主会话中且不能接受逻辑只读降级。

最可靠的工作流是拆分会话：

```text
可写实施会话：修改、测试、稳定差异
        ↓
整体只读父会话：启动 Reviewer 并完成严格复审
        ↓
返回可写实施会话：集中修复
```

如果父会话是 `workspace-write` 或 `danger-full-access`，且没有 `sandbox-denied` 运行时证据，只能判定为 Level B。不得因为 TOML 声明为 `read-only` 就升级为 Level A。

### 3.4 受控写入探针

写入探针不是常规复审步骤，只用于安装或运行时隔离验收：

- 只能在主协调 Agent 新建的一次性临时 Git 仓库中执行；
- 禁止在正式项目、生产目录、真实数据目录或用户主目录中执行；
- 只允许创建一个明确命名的探针文件；
- 命令语法错误、路径错误或 Shell 错误均判定为测试无效；
- 写入成功表示系统隔离失败；
- 只有明确的 sandbox denied 才能作为独立子 Agent 系统隔离证据；
- 测试结束后由主协调 Agent 删除整个临时仓库。

### 3.5 状态控制器记录

复杂任务应先使用：

```text
review_controller.py isolation
```

记录 `parent_sandbox`、`declared_sandbox`、`probe_result`、Agent 类型确认和证据摘要。设置 `--strict-readonly-required` 后，控制器会阻止在不满足 Level A 时计划或派发 Reviewer。

## 四、触发条件与风险分级

### 3.1 原则上触发

- 后端、前端、公共库或共享组件代码变化；
- Worker、调度、脚本、导出和数据处理逻辑变化；
- 数据库迁移、数据修复或消息契约变化；
- 运行配置、权限规则、序列化和公共状态变化；
- 核心业务、资金、权限、生产、历史兼容、高并发或数据一致性链路。

### 3.2 通常不触发

- 纯提交拆分；
- 仅修正提交信息；
- 不改变行为的文字、标点或排版；
- 未修改代码的只读分析；
- 已明确属于低风险且当前任务卡豁免的非行为变更。

### 3.3 风险级别与 Reviewer 数量

| 风险 | 典型场景 | 建议 Reviewer |
|---|---|---:|
| 低 | 局部、低频、无共享契约的小修复 | 1～2 |
| 中 | 单模块业务修改、数据库或异步链路 | 3～4 |
| 高 | 跨模块、公共组件、权限、并发、兼容 | 5～6 |
| 关键 | 生产、资金、数据迁移、核心状态机 | 第一轮 6，按需追加专项复核 |

“尽可能多开”应理解为：在风险、平台能力、Token 成本和职责独立性允许时，尽量覆盖不同审查维度；不是固定把数量开到上限。

## 五、专业 Reviewer 分工

### 4.1 功能与业务口径 Reviewer

检查：

- 目标问题是否真正解决；
- 正常、异常、补偿和失败路径；
- 业务计算、字段含义和状态流转；
- 是否只修表现没有修根因；
- 是否改变既有业务口径；
- 是否遗漏关键分支和不可达分支。

推荐 Agent：`cp_review_functional_business`。

### 4.2 回归与兼容 Reviewer

检查：

- 未修改正常路径是否保持原行为；
- 旧接口、旧前端、旧 Worker 和旧实例；
- 旧数据、旧缓存、旧消息和历史序列化；
- 公共方法、默认值、枚举和错误码；
- 灰度期间新旧版本共存；
- 修复 A 是否间接破坏 B。

推荐 Agent：`cp_review_compatibility_regression`。

### 4.3 权限与安全 Reviewer

检查：

- 认证、接口权限、数据权限和租户隔离；
- 水平和垂直越权、ID 枚举、资源归属；
- SQL / 命令注入、SSRF、路径穿越、XSS、CSRF；
- 文件上传下载、反序列化、敏感信息和日志脱敏；
- 新接口、新入口和默认配置是否绕过安全边界。

推荐 Agent：`cp_review_security_access`。

### 4.4 性能与资源 Reviewer

检查：

- SQL 数量、N+1、全表扫描、索引失效和长事务；
- 远程调用、Redis、MQ、文件、NAS 和对象存储 I/O；
- 线程、协程、进程、连接池、队列、缓存和临时文件；
- 大对象复制、重复序列化和高频日志；
- 开销是否位于高频路径；
- 开销是否随用户、任务、文件或数据量线性或更快增长；
- 无界并发、队列、缓存和重试。

推荐 Agent：`cp_review_performance_resources`。

### 4.5 数据与契约 Reviewer

检查：

- 数据库字段、索引、唯一约束、事务和锁；
- API 请求、响应、错误码和幂等键；
- Redis Key、TTL、序列化和缓存一致性；
- MQ 消息版本、ACK、重试、死信、顺序和重复消费；
- 文件格式、对象 Key 和历史数据兼容；
- 各层字段含义和成功边界是否一致。

推荐 Agent：`cp_review_data_contract`。

### 4.6 状态、并发与交互 Reviewer

检查：

- 空值、空集合、零值、最大最小值和时间边界；
- 重复提交、重复点击、重复回调和幂等；
- 并发竞争、锁顺序、超时、重试、取消和中断；
- 部分成功、部分失败、恢复和最终一致性；
- 页面刷新、路由切换、加载、空、错误和禁用状态；
- 异步竞态、资源释放和隐式依赖。

推荐 Agent：`cp_review_state_concurrency`。

### 4.7 测试与交付 Reviewer

检查：

- 最低定向验证是否能证明修改行为；
- 测试是否覆盖关键正常、异常和边界路径；
- 测试是否过度 Mock、依赖执行顺序或污染环境；
- 构建、导出、迁移和运行证据是否真实；
- CHANGELOG、提交边界、文档和实际差异是否一致；
- 失败、历史失败、未验证项是否被隐瞒。

推荐 Agent：`cp_review_test_delivery`。

## 六、实施前设计与影响审查

### 5.1 触发条件

以下任务在开始编码或生成迁移脚本前，优先执行一次轻量实施前审查：

- 新增或修改公共 API、消息、缓存、文件或序列化契约；
- 数据库表结构、索引、迁移、历史数据回填或新旧代码共存；
- 认证、接口权限、数据权限、租户隔离和关键安全边界；
- 核心业务状态机、资金、库存、任务状态和幂等成功边界；
- 跨服务拆分、数据所有权、异步链路和故障隔离；
- 高并发、资源预算、GPU 调度、NAS/对象存储迁移；
- 生产迁移、灰度、回滚困难或不可逆操作。

局部、低风险、无共享契约的小修复通常不执行实施前多 Agent 审查，避免流程成本超过收益。

### 5.2 前置输入

实施前必须先形成可审查方案，至少包含：

- 目标、非目标和业务成功边界；
- 当前事实、关键假设和未验证项；
- 受影响模块、调用链、数据和契约；
- 推荐方案与备选方案；
- 兼容、性能、安全、迁移、灰度和回滚考虑；
- 编码后最低验证和实施后复审计划。

不得让 Reviewer 在没有方案边界的情况下泛化讨论整个系统。

### 5.3 Reviewer 组合

默认选择 2～4 个职责互补的 Reviewer：

- 功能与业务；
- 回归与兼容；
- 权限与安全；
- 性能与资源；
- 数据与契约。

状态并发或测试交付 Reviewer 仅在方案本身涉及对应风险时加入。实施前 Reviewer 只审方案、契约、调用链和已知事实，不把尚未存在的代码问题写成已确认缺陷。

### 5.4 归并与门禁

主协调 Agent 收齐结果后：

1. 去重并按根因归并；
2. 区分方案缺陷、风险假设、证据缺口和范围外建议；
3. 更新推荐方案和实施边界；
4. 记录编码后必须验证的风险；
5. 只有阻塞设计问题解决后才开始实施。

实施前结论只能使用：通过、修订后通过、有阻塞问题、未完成。

### 5.5 与实施后预算关系

实施前 Reviewer 计入单功能边界累计 12 个 Reviewer 总预算。主协调 Agent应为实施后复审预留预算，不得在实施前消耗全部额度。

## 七、复审状态控制器

复杂任务优先使用 `scripts/review_controller.py` 保存确定性状态。控制器不创建 Agent，也不修改代码，只维护：

- 功能边界和安全上限；
- pre / post 阶段及当前轮次；
- 计划、已派发、活跃和已完成 Reviewer；
- 当前深度、累计 Reviewer 和剩余预算；
- 归并结论、集中修复轮次和最终结论。

建议流程：

```text
init → plan → dispatch → result → merge → repair（按需） → validate/status → close
```

上下文压缩或 Agent 切换后，必须先执行 `status` 或 `validate`，不能仅凭对话记忆继续派生 Reviewer。控制器限制比提示词更严格时，以控制器为准；控制器不得被用于突破平台更低的并发限制。

---

## 八、实施后复审前置条件

开始第一轮前，主协调 Agent 必须确认：

1. 当前功能边界已经完成修改；
2. 与改动直接相关的最低定向验证已经执行，或阻塞原因已记录；
3. `git diff` 已经稳定，不再进行边审边大改；
4. 基线 Commit、当前 HEAD、改动文件和差异范围明确；
5. 已记录 Reviewer TOML 声明与运行时隔离等级；严格任务必须满足 Level A，普通可写父会话只能按 Level B 报告；
6. 已确定风险级别、Reviewer 组合和预算；
7. 如启用长期任务记忆，已写入“复审启动检查点”。

复审启动检查点至少记录：

- 功能边界；
- 基线和差异范围；
- 第一轮 Reviewer 清单；
- 当前深度、轮次和剩余预算；
- 最低验证结果；
- 停止条件。

## 九、第一轮并行审查

### 6.1 派发要求

每个 Reviewer 的任务必须包含：

- 唯一职责；
- 审查文件和调用链范围；
- 不负责的内容；
- 当前轮次和逻辑深度；
- 功能边界和基线；
- 证据要求；
- 输出模板；
- 禁止修改、提交、推送、部署和继续派生；同时声明当前隔离等级，Level B 不得写成系统强制禁止；
- 当前 Reviewer 预算不是其可自行消费的授权。

### 6.2 等待要求

- 主协调 Agent 必须等待本轮适用 Reviewer 全部返回；
- Reviewer 运行期间不得收到一条问题就立即修改代码；
- Reviewer 失败或超时时，记录失败并判断是否重试一次、替换 Reviewer 或标记未验证；
- 不得因为某个 Reviewer 先返回“通过”就提前终止其他维度。

### 6.3 适合并行的工作

优先并行：

- 只读代码和调用链审查；
- 安全、兼容、性能和状态扫描；
- 测试证据检查；
- 文档或框架 API 核验；
- 日志、执行计划和差异分析。

谨慎并行：

- 多 Agent 同时修改同一工作树；
- 多 Agent 同时更新共享外部记忆；
- 多 Agent 同时执行有状态测试；
- 多 Agent 同时操作数据库、中间件和环境。

本复审工作流要求 Reviewer 行为只读，不并行写代码。是否具有系统级写入隔离必须由运行时证据决定。

## 十、结果归并与根因聚类

主协调 Agent 收齐结果后，必须完成：

1. 按文件、调用链和业务边界归并；
2. 删除完全重复的问题；
3. 将同一根因导致的多个表象合并；
4. 区分已确认、高概率、推测和未验证；
5. 对 Reviewer 结论冲突进行证据比较；
6. 标记问题是否由本次改动引入；
7. 按阻塞、高、中、低、建议分级；
8. 区分本次范围内问题和额外发现；
9. 为每个问题定义修复后验证方式；
10. 形成最小完整修复集合和修复顺序。

### 7.1 同根因合并示例

以下表象：

- 消息重试导致重复扣减；
- 消费者无幂等记录；
- 数据库没有唯一约束；
- ACK 早于业务提交；

应聚合为“消息消费幂等与成功边界不完整”，统一评估业务幂等键、唯一约束、事务提交、ACK、重试和并发测试，而不是拆成四次孤立修复。

### 7.2 冲突处理

Reviewer 冲突时：

1. 首先比较实际代码、配置、测试和运行证据；
2. 主协调 Agent 能直接裁决时，不新增 Agent；
3. 仍无法裁决且影响阻塞结论时，可在深度 2 启动一个专项第二意见 Reviewer；
4. 同一争议最多追加一次第二意见；
5. 仍无法确认时标记未验证并保留决策点。

---

## 十、最小完整修复集合

集中修复清单应满足：

- 能完整消除本次范围内的阻塞根因；
- 不把同根因拆成多次反复修改；
- 不顺手处理无关低优先级问题；
- 不改变未要求的公共契约和业务口径；
- 明确每项修改影响的验证和复审维度；
- 明确修复顺序和回滚点。

主协调 Agent 在形成修复集合后，再由实施 Agent统一修改。

禁止：

- Reviewer 直接改代码；
- 多个 Reviewer 同时写同一工作区；
- 为追求“一次修完”扩大到无关重构；
- 为减少轮次忽略新发现的高风险问题。

---

## 十一、修复后的验证和定向复核

### 9.1 集中修复后

1. 检查新的 `git diff`；
2. 重跑受影响的最低定向验证；
3. 更新复审台账中的问题状态；
4. 只对受影响维度启动下一轮 Reviewer；
5. 如果修改公共接口、公共组件、全局序列化、权限拦截器、消息公共模型或数据库公共字段，扩大复审范围。

### 9.2 不机械重跑全部 Reviewer

例如只修改 SQL 和事务，可以复核：

- 功能与业务；
- 数据与契约；
- 性能与资源；
- 测试与交付。

没有前端行为变化时，不必重复启动前端交互审查。

### 9.3 第三轮

只有以下情况进入第三轮：

- 第二轮仍发现阻塞问题；
- 修复再次改变公共边界；
- 证据冲突尚未闭环；
- 关键任务要求最终独立确认。

第三轮属于逻辑深度 3。第三轮 Reviewer 不得再建议自动派生新的 Reviewer。

---

## 十三、停止条件

### 10.1 正常停止

满足以下条件后结束自动复审：

- 所有阻塞问题已解决；
- 高等级问题已解决或由用户明确接受；
- 受影响的最低定向验证通过；
- 相关调用链和契约复审完成；
- 没有新引入的阻塞回归；
- 当前差异稳定；
- 未验证项和额外发现已明确记录。

### 10.2 受限停止

出现以下情况必须停止自动循环，但不得标记为通过：

- 达到最大深度；
- 达到最大复审轮次；
- 达到最大修复轮次；
- 达到 Reviewer 总量或平台并发上限；
- 工具不支持继续创建 Agent；
- 环境、权限或依赖缺失；
- Reviewer 冲突无法裁决；
- 继续修复会扩大任务边界；
- 需要用户决定业务口径、架构或风险接受。

停止时输出：

- 已完成的轮次和 Reviewer；
- 已解决问题；
- 剩余阻塞和未验证项；
- 达到的上限；
- 下一步需要的用户决策。

---

## 十三、Reviewer 标准输出

每个 Reviewer 必须使用结构化结果，至少包含：

```text
Reviewer：
轮次 / 深度：
功能边界：
基线 / 差异范围：
审查文件和调用链：
最终结论：通过 / 有非阻塞问题 / 有阻塞问题 / 未完成

发现列表：
- 问题 ID
- 严重等级
- 证据等级
- 文件、符号或配置位置
- 问题描述
- 影响和触发条件
- 根因判断
- 是否由本次改动引入
- 建议修复边界
- 修复后验证方式

未验证项：
建议追加专项复审：是 / 否，以及原因
```

问题必须以可行动、可复核的证据为中心。避免只给风格建议，除非风格问题会掩盖真实 Bug、性能或安全风险。

---

## 十四、主协调 Agent 复审台账

主协调 Agent 使用统一台账记录：

- Review Round；
- Reviewer 名称、职责、状态和耗时；
- 问题 ID、来源 Reviewer 和重复关系；
- 根因组；
- 严重等级和证据等级；
- 是否阻塞；
- 是否本次引入；
- 修复状态；
- 验证状态；
- 复核状态；
- 剩余预算。

不得把 Reviewer 的原始长日志全部复制到主进度文档。完整结果可以保存在外部记忆目录的 `reviews/<任务标识>/round-N/`，主进度只保留索引和归并结论。

---

## 十五、与长期任务记忆的结合

启用 `$long-running-task-memory` 时，至少持久化这些节点：

1. 复审计划和 Reviewer 预算确定；
2. 第一轮 Reviewer 已全部派发；
3. 第一轮结果收齐并完成归并；
4. 最小完整修复集合确定；
5. 集中修复完成；
6. 受影响验证完成；
7. 第二或第三轮复核完成；
8. 最终门禁结论形成。

只有主协调 Agent 写共享记忆。Reviewer 只返回结构化结果或写入自己被明确分配的独立报告文件。

---

## 十六、最终结论

最终结论只能使用：

- 通过，无阻塞项；
- 有非阻塞问题；
- 有阻塞问题；
- 达到复审上限，仍有阻塞或未验证项；
- 工具或环境受限，未完成严格独立复审；
- 不适用。

不得使用“看起来没问题”“大概通过”“应该不会影响”等不可复核结论。


> 最终原则：独立推理不等于权限隔离；TOML 声明不等于运行时事实；严格只读必须由父会话或有效沙箱证据保证。
