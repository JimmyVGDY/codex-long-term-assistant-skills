# 多 Agent 独立复审与最少有效修复轮次工作流

> 本工作流用于真实代码或可执行行为发生变化后的提交前复审。它不能替代构建、运行测试、数据验证或生产验收。

## 一、目标

多 Agent 复审的目标不是无上限增加 Reviewer，而是：

- 在第一轮尽可能完整地发现功能、回归、安全、性能、数据和状态风险；
- 把噪声工作移出主线程，保持主协调 Agent 聚焦目标、授权、决策和最终交付；
- 等待本轮结果收齐后统一去重、归因和分级；
- 将同一根因导致的多个表象合并为一组完整修复；
- 降低“改一处、审一次、再改一处”的多次回炉；
- 对修复后的受影响范围进行定向复核，而不是机械重跑所有 Reviewer。

正式原则：

> **一次发现、统一归因、集中修复、定向复核，追求最少有效修复轮次。**

“最少”不等于隐瞒问题。任何新发现的阻塞问题都必须如实保留和处理。

---

## 二、默认安全参数

除非项目规则或用户明确设置更严格上限，采用：

```text
MAX_REVIEW_AGENT_DEPTH = 3
MAX_REVIEW_ROUNDS = 3
MAX_PARALLEL_REVIEWERS = 6
MAX_TOTAL_REVIEW_AGENTS_PER_BOUNDARY = 12
MAX_REPAIR_ROUNDS = 3
```

含义：

- 深度 0：主协调 Agent；
- 深度 1：第一轮专业 Reviewer；
- 深度 2：冲突裁决、证据补足或专项第二意见；
- 深度 3：最终定向复核；
- 深度达到 3 后禁止继续派生 Reviewer；
- 同一功能边界最多自动执行 3 轮复审和 3 轮集中修复；
- 同时运行的 Reviewer 默认不超过 6；
- 全部轮次累计 Reviewer 不超过 12。

当前平台、配置、权限或用户要求的上限更低时，采用更低值。不得通过拆成等价工具调用、隐藏子任务或重复命名规避上限。

### 2.1 单一协调者

- 只有主协调 Agent 负责派发 Reviewer、汇总结果、维护预算和决定下一轮；
- Reviewer 默认不得自行派生子 Reviewer；
- 需要补充专家时，Reviewer 只提出“建议追加专项复审”，由主协调 Agent 判断是否在预算内执行；
- 主协调 Agent 是共享复审台账和外部记忆文档的唯一写入者。

---

## 三、触发条件与风险分级

### 3.1 原则上触发

- 后端、前端、公共库或共享组件代码变化；
- Worker、调度、脚本、导出和数据处理逻辑变化；
- 数据库迁移、数据修复或消息契约变化；
- 运行配置、权限规则、序列化和公共状态变化；
- 核心业务、资金、权限、生产、历史兼容、高并发或数据一致性链路。

### 3.2 通常不触发

- 纯提交拆分；
- 仅修正提交信息；
- 不改变行为的文字、标点或排版；
- 未修改代码的只读分析；
- 已明确属于低风险且当前任务卡豁免的非行为变更。

### 3.3 风险级别与 Reviewer 数量

| 风险 | 典型场景 | 建议 Reviewer |
|---|---|---:|
| 低 | 局部、低频、无共享契约的小修复 | 1～2 |
| 中 | 单模块业务修改、数据库或异步链路 | 3～4 |
| 高 | 跨模块、公共组件、权限、并发、兼容 | 5～6 |
| 关键 | 生产、资金、数据迁移、核心状态机 | 第一轮 6，按需追加专项复核 |

“尽可能多开”应理解为：在风险、平台能力、Token 成本和职责独立性允许时，尽量覆盖不同审查维度；不是固定把数量开到上限。

---

## 四、专业 Reviewer 分工

### 4.1 功能与业务口径 Reviewer

检查：

- 目标问题是否真正解决；
- 正常、异常、补偿和失败路径；
- 业务计算、字段含义和状态流转；
- 是否只修表现没有修根因；
- 是否改变既有业务口径；
- 是否遗漏关键分支和不可达分支。

推荐 Agent：`cp_review_functional_business`。

### 4.2 回归与兼容 Reviewer

检查：

- 未修改正常路径是否保持原行为；
- 旧接口、旧前端、旧 Worker 和旧实例；
- 旧数据、旧缓存、旧消息和历史序列化；
- 公共方法、默认值、枚举和错误码；
- 灰度期间新旧版本共存；
- 修复 A 是否间接破坏 B。

推荐 Agent：`cp_review_compatibility_regression`。

### 4.3 权限与安全 Reviewer

检查：

- 认证、接口权限、数据权限和租户隔离；
- 水平和垂直越权、ID 枚举、资源归属；
- SQL / 命令注入、SSRF、路径穿越、XSS、CSRF；
- 文件上传下载、反序列化、敏感信息和日志脱敏；
- 新接口、新入口和默认配置是否绕过安全边界。

推荐 Agent：`cp_review_security_access`。

### 4.4 性能与资源 Reviewer

检查：

- SQL 数量、N+1、全表扫描、索引失效和长事务；
- 远程调用、Redis、MQ、文件、NAS 和对象存储 I/O；
- 线程、协程、进程、连接池、队列、缓存和临时文件；
- 大对象复制、重复序列化和高频日志；
- 开销是否位于高频路径；
- 开销是否随用户、任务、文件或数据量线性或更快增长；
- 无界并发、队列、缓存和重试。

推荐 Agent：`cp_review_performance_resources`。

### 4.5 数据与契约 Reviewer

检查：

- 数据库字段、索引、唯一约束、事务和锁；
- API 请求、响应、错误码和幂等键；
- Redis Key、TTL、序列化和缓存一致性；
- MQ 消息版本、ACK、重试、死信、顺序和重复消费；
- 文件格式、对象 Key 和历史数据兼容；
- 各层字段含义和成功边界是否一致。

推荐 Agent：`cp_review_data_contract`。

### 4.6 状态、并发与交互 Reviewer

检查：

- 空值、空集合、零值、最大最小值和时间边界；
- 重复提交、重复点击、重复回调和幂等；
- 并发竞争、锁顺序、超时、重试、取消和中断；
- 部分成功、部分失败、恢复和最终一致性；
- 页面刷新、路由切换、加载、空、错误和禁用状态；
- 异步竞态、资源释放和隐式依赖。

推荐 Agent：`cp_review_state_concurrency`。

### 4.7 测试与交付 Reviewer

检查：

- 最低定向验证是否能证明修改行为；
- 测试是否覆盖关键正常、异常和边界路径；
- 测试是否过度 Mock、依赖执行顺序或污染环境；
- 构建、导出、迁移和运行证据是否真实；
- CHANGELOG、提交边界、文档和实际差异是否一致；
- 失败、历史失败、未验证项是否被隐瞒。

推荐 Agent：`cp_review_test_delivery`。

---

## 五、复审前置条件

开始第一轮前，主协调 Agent 必须确认：

1. 当前功能边界已经完成修改；
2. 与改动直接相关的最低定向验证已经执行，或阻塞原因已记录；
3. `git diff` 已经稳定，不再进行边审边大改；
4. 基线 Commit、当前 HEAD、改动文件和差异范围明确；
5. Reviewer 全部为只读；
6. 已确定风险级别、Reviewer 组合和预算；
7. 如启用长期任务记忆，已写入“复审启动检查点”。

复审启动检查点至少记录：

- 功能边界；
- 基线和差异范围；
- 第一轮 Reviewer 清单；
- 当前深度、轮次和剩余预算；
- 最低验证结果；
- 停止条件。

---

## 六、第一轮并行审查

### 6.1 派发要求

每个 Reviewer 的任务必须包含：

- 唯一职责；
- 审查文件和调用链范围；
- 不负责的内容；
- 当前轮次和逻辑深度；
- 功能边界和基线；
- 证据要求；
- 输出模板；
- 禁止修改、提交、推送、部署和继续派生；
- 当前 Reviewer 预算不是其可自行消费的授权。

### 6.2 等待要求

- 主协调 Agent 必须等待本轮适用 Reviewer 全部返回；
- Reviewer 运行期间不得收到一条问题就立即修改代码；
- Reviewer 失败或超时时，记录失败并判断是否重试一次、替换 Reviewer 或标记未验证；
- 不得因为某个 Reviewer 先返回“通过”就提前终止其他维度。

### 6.3 适合并行的工作

优先并行：

- 只读代码和调用链审查；
- 安全、兼容、性能和状态扫描；
- 测试证据检查；
- 文档或框架 API 核验；
- 日志、执行计划和差异分析。

谨慎并行：

- 多 Agent 同时修改同一工作树；
- 多 Agent 同时更新共享外部记忆；
- 多 Agent 同时执行有状态测试；
- 多 Agent 同时操作数据库、中间件和环境。

本复审工作流默认只读，不并行写代码。

---

## 七、结果归并与根因聚类

主协调 Agent 收齐结果后，必须完成：

1. 按文件、调用链和业务边界归并；
2. 删除完全重复的问题；
3. 将同一根因导致的多个表象合并；
4. 区分已确认、高概率、推测和未验证；
5. 对 Reviewer 结论冲突进行证据比较；
6. 标记问题是否由本次改动引入；
7. 按阻塞、高、中、低、建议分级；
8. 区分本次范围内问题和额外发现；
9. 为每个问题定义修复后验证方式；
10. 形成最小完整修复集合和修复顺序。

### 7.1 同根因合并示例

以下表象：

- 消息重试导致重复扣减；
- 消费者无幂等记录；
- 数据库没有唯一约束；
- ACK 早于业务提交；

应聚合为“消息消费幂等与成功边界不完整”，统一评估业务幂等键、唯一约束、事务提交、ACK、重试和并发测试，而不是拆成四次孤立修复。

### 7.2 冲突处理

Reviewer 冲突时：

1. 首先比较实际代码、配置、测试和运行证据；
2. 主协调 Agent 能直接裁决时，不新增 Agent；
3. 仍无法裁决且影响阻塞结论时，可在深度 2 启动一个专项第二意见 Reviewer；
4. 同一争议最多追加一次第二意见；
5. 仍无法确认时标记未验证并保留决策点。

---

## 八、最小完整修复集合

集中修复清单应满足：

- 能完整消除本次范围内的阻塞根因；
- 不把同根因拆成多次反复修改；
- 不顺手处理无关低优先级问题；
- 不改变未要求的公共契约和业务口径；
- 明确每项修改影响的验证和复审维度；
- 明确修复顺序和回滚点。

主协调 Agent 在形成修复集合后，再由实施 Agent统一修改。

禁止：

- Reviewer 直接改代码；
- 多个 Reviewer 同时写同一工作区；
- 为追求“一次修完”扩大到无关重构；
- 为减少轮次忽略新发现的高风险问题。

---

## 九、修复后的验证和定向复核

### 9.1 集中修复后

1. 检查新的 `git diff`；
2. 重跑受影响的最低定向验证；
3. 更新复审台账中的问题状态；
4. 只对受影响维度启动下一轮 Reviewer；
5. 如果修改公共接口、公共组件、全局序列化、权限拦截器、消息公共模型或数据库公共字段，扩大复审范围。

### 9.2 不机械重跑全部 Reviewer

例如只修改 SQL 和事务，可以复核：

- 功能与业务；
- 数据与契约；
- 性能与资源；
- 测试与交付。

没有前端行为变化时，不必重复启动前端交互审查。

### 9.3 第三轮

只有以下情况进入第三轮：

- 第二轮仍发现阻塞问题；
- 修复再次改变公共边界；
- 证据冲突尚未闭环；
- 关键任务要求最终独立确认。

第三轮属于逻辑深度 3。第三轮 Reviewer 不得再建议自动派生新的 Reviewer。

---

## 十、停止条件

### 10.1 正常停止

满足以下条件后结束自动复审：

- 所有阻塞问题已解决；
- 高等级问题已解决或由用户明确接受；
- 受影响的最低定向验证通过；
- 相关调用链和契约复审完成；
- 没有新引入的阻塞回归；
- 当前差异稳定；
- 未验证项和额外发现已明确记录。

### 10.2 受限停止

出现以下情况必须停止自动循环，但不得标记为通过：

- 达到最大深度；
- 达到最大复审轮次；
- 达到最大修复轮次；
- 达到 Reviewer 总量或平台并发上限；
- 工具不支持继续创建 Agent；
- 环境、权限或依赖缺失；
- Reviewer 冲突无法裁决；
- 继续修复会扩大任务边界；
- 需要用户决定业务口径、架构或风险接受。

停止时输出：

- 已完成的轮次和 Reviewer；
- 已解决问题；
- 剩余阻塞和未验证项；
- 达到的上限；
- 下一步需要的用户决策。

---

## 十一、Reviewer 标准输出

每个 Reviewer 必须使用结构化结果，至少包含：

```text
Reviewer：
轮次 / 深度：
功能边界：
基线 / 差异范围：
审查文件和调用链：
最终结论：通过 / 有非阻塞问题 / 有阻塞问题 / 未完成

发现列表：
- 问题 ID
- 严重等级
- 证据等级
- 文件、符号或配置位置
- 问题描述
- 影响和触发条件
- 根因判断
- 是否由本次改动引入
- 建议修复边界
- 修复后验证方式

未验证项：
建议追加专项复审：是 / 否，以及原因
```

问题必须以可行动、可复核的证据为中心。避免只给风格建议，除非风格问题会掩盖真实 Bug、性能或安全风险。

---

## 十二、主协调 Agent 复审台账

主协调 Agent 使用统一台账记录：

- Review Round；
- Reviewer 名称、职责、状态和耗时；
- 问题 ID、来源 Reviewer 和重复关系；
- 根因组；
- 严重等级和证据等级；
- 是否阻塞；
- 是否本次引入；
- 修复状态；
- 验证状态；
- 复核状态；
- 剩余预算。

不得把 Reviewer 的原始长日志全部复制到主进度文档。完整结果可以保存在外部记忆目录的 `reviews/<任务标识>/round-N/`，主进度只保留索引和归并结论。

---

## 十三、与长期任务记忆的结合

启用 `$long-running-task-memory` 时，至少持久化这些节点：

1. 复审计划和 Reviewer 预算确定；
2. 第一轮 Reviewer 已全部派发；
3. 第一轮结果收齐并完成归并；
4. 最小完整修复集合确定；
5. 集中修复完成；
6. 受影响验证完成；
7. 第二或第三轮复核完成；
8. 最终门禁结论形成。

只有主协调 Agent 写共享记忆。Reviewer 只返回结构化结果或写入自己被明确分配的独立报告文件。

---

## 十四、最终结论

最终结论只能使用：

- 通过，无阻塞项；
- 有非阻塞问题；
- 有阻塞问题；
- 达到复审上限，仍有阻塞或未验证项；
- 工具或环境受限，未完成严格独立复审；
- 不适用。

不得使用“看起来没问题”“大概通过”“应该不会影响”等不可复核结论。
