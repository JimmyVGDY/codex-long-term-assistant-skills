## 十一、修复后的验证和定向复核

### 9.1 集中修复后

1. 检查新的 `git diff`；
2. 重跑受影响的最低定向验证；
3. 更新复审台账中的问题状态；
4. 只对受影响维度启动下一轮 Reviewer；
5. 如果修改公共接口、公共组件、全局序列化、权限拦截器、消息公共模型或数据库公共字段，扩大复审范围。

### 9.2 不机械重跑全部 Reviewer

例如只修改 SQL 和事务，可以复核：

- 功能与业务；
- 数据与契约；
- 性能与资源；
- 测试与交付。

没有前端行为变化时，不必重复启动前端交互审查。

### 9.3 第三轮

只有以下情况进入第三轮：

- 第二轮仍发现阻塞问题；
- 修复再次改变公共边界；
- 证据冲突尚未闭环；
- 关键任务要求最终独立确认。

第三轮属于逻辑深度 3。第三轮 Reviewer 不得再建议自动派生新的 Reviewer。

## 十三、停止条件

### 10.1 正常停止

满足以下条件后结束自动复审：

- 所有阻塞问题已解决；
- 高等级问题已解决或由用户明确接受；
- 受影响的最低定向验证通过；
- 相关调用链和契约复审完成；
- 没有新引入的阻塞回归；
- 当前差异稳定；
- 未验证项和额外发现已明确记录。

### 10.2 受限停止

出现以下情况必须停止自动循环，但不得标记为通过：

- 达到最大深度；
- 达到最大复审轮次；
- 达到最大修复轮次；
- 达到 Reviewer 总量或平台并发上限；
- 工具不支持继续创建 Agent；
- 环境、权限或依赖缺失；
- Reviewer 冲突无法裁决；
- 继续修复会扩大任务边界；
- 需要用户决定业务口径、架构或风险接受。

停止时输出：

- 已完成的轮次和 Reviewer；
- 已解决问题；
- 剩余阻塞和未验证项；
- 达到的上限；
- 下一步需要的用户决策。

## 十三、Reviewer 标准输出

每个 Reviewer 必须使用结构化结果，至少包含：

```text
Reviewer：
轮次 / 深度：
功能边界：
基线 / 差异范围：
审查文件和调用链：
最终结论：通过 / 有非阻塞问题 / 有阻塞问题 / 未完成

发现列表：
- 问题 ID
- 严重等级
- 证据等级
- 文件、符号或配置位置
- 问题描述
- 影响和触发条件
- 根因判断
- 是否由本次改动引入
- 建议修复边界
- 修复后验证方式

未验证项：
建议追加专项复审：是 / 否，以及原因
```

问题必须以可行动、可复核的证据为中心。避免只给风格建议，除非风格问题会掩盖真实 Bug、性能或安全风险。

## 十四、主协调 Agent 复审台账

主协调 Agent 使用统一台账记录：

- Review Round；
- Reviewer 名称、职责、状态和耗时；
- 问题 ID、来源 Reviewer 和重复关系；
- 根因组；
- 严重等级和证据等级；
- 是否阻塞；
- 是否本次引入；
- 修复状态；
- 验证状态；
- 复核状态；
- 剩余预算。

不得把 Reviewer 的原始长日志全部复制到主进度文档。完整结果可以保存在外部记忆目录的 `reviews/<任务标识>/round-N/`，主进度只保留索引和归并结论。

## 十五、与长期任务记忆的结合

启用 `$long-running-task-memory` 时，至少持久化这些节点：

1. 复审计划和 Reviewer 预算确定；
2. 第一轮 Reviewer 已全部派发；
3. 第一轮结果收齐并完成归并；
4. 最小完整修复集合确定；
5. 集中修复完成；
6. 受影响验证完成；
7. 第二或第三轮复核完成；
8. 最终门禁结论形成。

只有主协调 Agent 写共享记忆。Reviewer 只返回结构化结果或写入自己被明确分配的独立报告文件。
