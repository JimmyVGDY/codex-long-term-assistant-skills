# 实施前审查与状态控制器

## 一、何时做实施前审查

优先用于：公共 API/消息/缓存/序列化契约、数据库迁移、权限边界、核心状态机、跨服务数据所有权、高并发资源预算、生产迁移和困难回滚。

局部、低风险、无共享契约的小修复通常不启动实施前多 Agent 审查。

## 二、最小输入

实施前先形成可审查方案：目标与非目标、成功边界、已确认事实与假设、影响模块与契约、推荐方案和备选方案、兼容/安全/性能/迁移/回滚、编码后最低验证。

不得让 Reviewer 在没有方案边界的情况下讨论整个系统。

## 三、Reviewer 组合

默认 1～2 个职责互补 Reviewer；关键任务最多 3 个，但实施前默认预算仍由控制器限制为 2，放宽必须显式配置。

- 功能/业务、数据/契约通常使用 `terra-medium`；
- 兼容、性能初筛可使用 `luna-medium`；
- 只有明确命中安全、并发、不可逆迁移或核心状态风险时，允许一个 Reviewer 使用 `terra-high`。

实施前只审方案、契约、调用链和已知事实，不能把尚不存在的代码问题写成已确认缺陷。

## 四、归并门禁

收齐结果后去重、按根因归并，区分方案缺陷、风险假设、证据缺口和范围外建议。只有阻塞设计问题解决后才开始实施。

结论只能为：通过、修订后通过、有阻塞问题、未完成。

## 五、状态控制器

`scripts/review_controller.py` 只维护台账，不负责真正启动 Agent。推荐顺序：

```text
init -> isolation -> plan -> dispatch -> result -> merge -> repair(按需) -> validate/status -> close
```

控制器记录功能边界、风险、隔离、预算、packet hash、模型档位、派发、结果和停止状态。上下文压缩或 Agent 切换后，先运行 `status` 或 `validate`，不能只凭对话记忆继续。

实施前 Reviewer 计入单功能边界累计 6 个默认预算，必须给实施后定向复审预留空间。
