## 十、Git、CHANGELOG 和交付

### 10.1 提交前检查

检查 `git status`、`git diff`、无关改动、大范围格式化、临时和日志文件、调试代码、敏感信息、锁文件、环境配置和外部记忆文档。

除非明确授权，不推送、不创建 PR、不合并、不强推。

### 10.2 功能边界和提交拆分

一个独立 Bug、功能、接口调整、性能、安全、兼容或迁移通常构成一个功能边界。互不依赖的边界应独立提交。

多个修改只有共同存在才能构成可构建、可验证的完整行为时才可合并，并说明不可拆分原因。

纯提交拆分、提交信息修正和无行为变化的格式修改不是新功能边界。

### 10.3 CHANGELOG

优先遵循当前项目既有规范，例如：

- 每功能提交一条；
- 每 PR 一条；
- 发布时统一维护；
- Conventional Commits、Changesets 或自动生成。

当前项目已有 `CHANGELOG.md` 且任务明确约束按功能边界更新时，应在最终提交前更新，内容必须与实际变更和验证一致。

不得：

- 用 CHANGELOG 替代测试和复审；
- 记录未完成或未验证内容为已完成；
- 把外部任务卡、计划和交接记录写入项目 CHANGELOG；
- 擅自创建与项目规范冲突的新 CHANGELOG。

### 10.4 提交信息

优先项目既有规范。没有明确规范时使用：

```text
<type> |> 中文功能摘要:关键实现与实际验证
```

推荐类型：

- `feat`：新增功能；
- `fix`：Bug 修复；
- `perf`：性能优化；
- `refactor`：不改变对外行为的重构；
- `test`：测试；
- `docs`：文档；
- `chore`：构建、工具和维护；
- `security`：项目允许时用于安全修复。

示例：

```text
fix |> 修复视频任务状态回写:增加幂等校验并完成相关后端定向测试
perf |> 优化订单批量查询:消除循环查询并验证执行计划
feat |> 增加任务取消能力:补充状态流转和接口验证
```

不得使用“优化代码”“修复问题”“更新内容”等无法识别边界的摘要，不得写入未执行的验证。

### 10.5 单功能边界交付顺序

1. 修改；
2. 最低定向验证；
3. 稳定差异；
4. 独立或兼容复审；
5. 修复阻塞项；
6. 重新验证和复审；
7. 更新正式文档或 CHANGELOG；
8. 检查差异；
9. 创建提交并返回真实 Hash；
10. 根据授权停止、推送或继续下一边界。

### 10.6 本地提交但不推送

完成修改、验证、复审、文档和差异检查后创建本地提交，返回真实 Commit Hash，然后停止，禁止推送。

## 十一、最终交付格式

复杂任务最终报告按需包含：

### 执行摘要

- 所属项目和执行模式；
- 目标、实际完成和未完成；
- 是否修改代码、配置、数据库和环境；
- 当前提交、推送、部署、重启和生效状态。

### 修改与验证

- 文件和关键改动；
- 实际命令；
- 后端测试、前端构建、Worker、导出、迁移和全量测试结果；
- 失败项、关系判断和未执行原因。

### 独立复审

- 门禁类型；
- Reviewer / 上下文；
- 差异范围；
- 六维结论；
- 阻塞和非阻塞问题；
- 最终结论。

### 影响与状态

- 性能、兼容、安全、权限、使用体验和资源；
- CHANGELOG、提交信息和 Hash；
- 生产制品、重启、版本加载、健康和功能生效层级；
- 风险、未验证项和需要外部执行的操作。

不适用项可省略，但失败、未验证、授权边界和风险不得省略。
