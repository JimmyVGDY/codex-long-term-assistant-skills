# 研发质量、验证、生产与 Git 交付工作流

> 涉及代码修改、可执行行为、环境操作、独立复审或 Git 交付时加载。本工作流定义质量门禁，不替代当前项目既有测试、发布和审计规范。

## 一、任务类型与响应模式

### 1.1 代码审查、分析和优化

按需输出：

- 功能说明；
- 当前问题和目标；
- Bug、空值、并发、SQL、事务、性能、安全、兼容和维护问题；
- 推荐方案、修改边界和收益；
- 完整代码、补丁或明确修改点；
- 实际验证结果和额外发现。

不存在的类别省略，不机械填满模板。

### 1.2 故障排查

按需输出：

1. 问题现象；
2. 已知证据和证据等级；
3. 日志、配置、监控和最近变更分析；
4. 多个可能原因，按发生概率、风险和验证成本排序；
5. 验证步骤，每步说明执行、观察和不同结果含义；
6. 临时止血、正式方案、长期优化和预防措施。

不得在证据不足时武断宣布唯一根因。

### 1.3 系统和架构设计

按需包含需求、流程、模块、边界、Mermaid 架构图、数据库和索引、接口、缓存、消息、搜索、权限、部署、高并发、高可用、成本、风险、分阶段路线和验收。

简单系统不机械引入微服务、消息队列、Redis、Elasticsearch 和 Kubernetes。

### 1.4 技术文档和报告

默认 Markdown，语言正式、专业、中立、可直接交付，不夸大未验证结论。简单文档不机械包含全部章节。

---

## 二、修改前工作流

真正修改前必须完成适用项：

1. 确认项目、仓库、分支和基线 Commit；
2. 确认执行模式和独立授权边界；
3. 阅读目标代码完整上下文和关键调用链；
4. 明确目标、非目标、修改范围和禁止范围；
5. 识别接口、数据库、缓存、消息、文件和配置契约；
6. 明确最低定向验证、复审和验收标准；
7. 高风险任务准备功能开关、灰度、停止和回滚方案。

信息充分且属于已授权范围时直接执行，不为低风险和可逆细节反复询问。

---

## 三、测试选择原则

测试必须根据实际改动、影响范围和风险选择，不机械执行全部测试，也不得以全量测试耗时或存在历史失败为由跳过与本次修改直接相关的最低验证。

### 3.1 工具方法

验证正常、空值、边界、异常输入和并发安全。

### 3.2 数据库逻辑

验证 SQL、执行计划、事务提交和回滚、锁冲突、并发更新、唯一约束和数据一致性。

### 3.3 API

验证正常、非法参数、认证、权限、契约、错误码、幂等和旧调用方兼容。

### 3.4 并发逻辑

验证重复执行、竞争、锁超时、死锁、取消、资源释放和最终一致性。

### 3.5 消息队列和任务

验证消息丢失、重复消费、ACK、重试、死信、幂等、堆积、超时、取消和恢复。

### 3.6 文件

验证空文件、大文件、损坏、重复、中断、超时、恢复、编码、临时文件和路径安全。

### 3.7 SSE / WebSocket

验证连接中断、心跳、重连、重复消息、顺序、落库、上下文、页面切换和取消。

### 3.8 AI 输出

验证 Schema、空和非法输出、超时、重试、降级、Prompt 注入、结构化修复和业务校验。

## 四、按改动类型的最低定向验证门槛

只要修改代码、脚本、Worker、调度、导出、迁移或其他可执行行为，必须完成适用的最低验证。不得只静态阅读后直接提交。

### 4.1 后端改动

至少执行一种能够直接证明修改行为的验证：

- 相关单元、Service、Controller 或 API 测试；
- 相关数据库、缓存、MQ、任务或状态流转测试；
- 明确输入和输出的最小可复现验证。

如果环境客观不完整，报告阻塞、未验证范围和风险，不得表述为通过。

### 4.2 前端改动

至少执行项目正式生产构建。npm 项目默认：

```bash
npm run build
```

并根据改动验证正常、加载、空、错误、禁用、重复点击、刷新、路由、权限、超时、竞态和前后端一致性。

### 4.3 脚本、Worker 和调度

至少实际运行脚本、执行单测、手动触发 Worker / 调度或完成最小复现。

检查输入、输出、异常退出、重复执行、幂等、超时、重试、中断、资源、状态、日志和重启恢复。

### 4.4 CSV、Excel、导出和数据文件

必须实际生成或读取代表性样例，检查：

- 表头名称和顺序；
- 字段映射、数据类型和空值；
- 金额、数量、比例、合计和小计；
- 日期时间、格式、分隔符、引号和转义；
- 字符编码、中文乱码和目标软件打开；
- 读取后与源数据一致。

大数据量还需检查流式处理、内存、临时文件、耗时、大小和失败清理。

### 4.5 数据库迁移和修复脚本

至少验证语法、影响范围、正向执行、重复执行或幂等、失败补偿、历史兼容、新旧代码共存、执行计划和锁风险。

生产执行仍需单独生产授权。

### 4.6 配置改动

区分纯文字、构建配置和运行行为配置。会改变运行行为的配置必须验证加载方式、默认值、缺失行为、环境差异、是否重启、灰度和回滚。

### 4.7 验证失败报告

失败时必须记录：

- 实际命令或步骤；
- 失败测试、阶段和错误摘要；
- 是否可复现；
- 与本次改动的关系和证据等级；
- 是否阻塞当前提交；
- 是否为修改前已存在的失败。

“高概率与本次无关”仍然不是“已确认无关”。

---

## 五、对抗性验证

核心链路、并发、状态、数据一致性和生产风险改动，应覆盖：

- 正常、异常、空值和边界；
- 极端数据量；
- 重复提交和重复回调；
- 并发竞争、超时、重试、中断和取消；
- 部分成功和部分失败；
- 资源释放和失败恢复；
- 旧数据、旧调用方、新旧版本和历史配置兼容。

重点发现：

- 空指针、越界、状态错乱和重复处理；
- 数据不一致、死锁、连接和线程泄漏；
- 协程、文件句柄和临时文件泄漏；
- 缓存污染、重试风暴和异常未收敛；
- 旧问题消失但转移到其他链路。

---

## 六、性能和资源验证

涉及性能影响时尽量建立修改前基线并对比：

- QPS、平均耗时、P95、P99 和错误率；
- SQL 数量、耗时、扫描行数和执行计划；
- 远程调用次数和消息耗时；
- CPU、内存、GC、线程、协程和进程；
- 连接池、队列、消息积压和文件 I/O；
- Event Loop 延迟、Token、GPU 显存和利用率。

不得新增不必要的 SQL、全表扫描、远程调用、序列化、大对象复制、线程进程、锁竞争、长事务、长连接、高频日志、无界缓存、无界队列和无限重试。

无法完成完整压测时，只能表述：

> 从代码路径和已执行的定向验证看，未发现明显新增性能开销；尚未完成完整性能压测。

不得声称“性能完全不受影响”。

## 七、独立复审与多 Agent 审查门禁

### 7.1 复审目的

复审用于降低修复后产生新 Bug、影响原有功能、改变业务口径、引入权限或安全漏洞、增加性能资源负担以及产生新的状态和边界问题。复审不能替代运行测试。

### 7.2 触发条件

真实修改运行行为的代码或可执行内容时原则上触发，包括后端、前端、公共库、脚本、Worker、调度、数据处理、导出、迁移和逻辑配置。

通常不触发：

- 纯提交拆分或提交信息修正；
- 仅调整 CHANGELOG 排版；
- 只读排查和未修改代码的静态分析；
- 不改变行为的普通文字修正。

生产、权限、资金、数据迁移、核心状态和高并发链路不得无理由豁免。

### 7.3 首选：多 Agent 严格独立门禁

条件允许时组合 `$multi-agent-independent-review`，按风险启动职责不同的只读 Reviewer，对功能与口径、回归与兼容、权限与安全、性能与资源、数据与契约、状态与并发以及测试与交付进行并行审查。

必须遵循：

- Reviewer 只读，不修改、提交、推送、部署、重启或执行生产写操作；
- 第一轮 Reviewer 全部返回前，不边审边零散改代码；
- 主协调 Agent 统一去重、根因聚类、冲突裁决和分级；
- 形成“最小完整修复集合”后集中修复；
- 修复后只复核受影响范围，公共边界变化时扩大范围；
- 默认最大审查深度 3、最大复审轮次 3、最大并行 Reviewer 6、单功能边界最多 12 个 Reviewer、最大集中修复轮次 3；
- 达到上限后停止自动循环，保留阻塞和未验证项，不得伪称通过。

详细流程、Reviewer 角色、输出模板和停止规则由 `$multi-agent-independent-review` 定义。启用 `$long-running-task-memory` 时，复审计划、派发、结果收齐、归并、集中修复、重新验证和最终复核都必须形成检查点；只有主协调 Agent 更新共享记忆。

### 7.4 受限环境兼容门禁

仅在工具客观不支持独立 Reviewer，且任务不属于必须严格门禁时使用：

1. 实施完成后切换到只读复审阶段；
2. 重新读取实际 `git diff`、完整上下文、调用链、契约和测试证据；
3. 不以实施过程中的预期作为结论；
4. 按六维输出问题、证据、等级、阻塞和未验证项；
5. 明确标记“隔离二次复审，不等同于真正独立 Reviewer”；
6. 是否允许提交由当前任务卡或用户授权决定。

禁止把兼容门禁伪称为严格独立复审。

### 7.5 标准顺序

```text
完成功能边界修改
    ↓
执行最低定向验证
    ↓
稳定当前 git diff
    ↓
多 Agent 并行独立复审或受限兼容复审
    ↓
统一归并并形成最小完整修复集合
    ↓
实施者集中修复阻塞问题
    ↓
重新执行受影响验证
    ↓
定向复核受影响范围
    ↓
更新正式文档或 CHANGELOG（按项目规范）
    ↓
检查差异并提交
```

复审后修改相关代码，必须重新验证和复核受影响范围。

### 7.6 六个核心维度

1. 权限与越权；
2. 安全；
3. 功能正确性与业务口径；
4. 原有功能回归与兼容性；
5. 性能与资源负担；
6. 状态、交互与新边界。

测试证据和交付边界作为补充专业维度独立检查。

### 7.7 输出和结论

输出功能边界、差异基线、文件、调用链、Reviewer 和轮次、六维结论、归并问题、等级、根因组、是否阻塞、未验证项、修复轮次和最终结论。

等级：阻塞、高、中、低、建议。

最终结论只能使用：

- 通过，无阻塞项；
- 有非阻塞问题；
- 有阻塞问题；
- 达到复审上限，仍有阻塞或未验证项；
- 工具或环境受限，未完成严格独立复审；
- 不适用。

Reviewer 只报告，实施者修改。阻塞问题解决前不得形成最终交付。

## 八、完成定义

任务只有满足所有适用条件才算完成：

1. 目标问题已处理且未扩大范围；
2. 代码可编译或构建；
3. 最低定向验证已执行；
4. 回归、兼容、安全、性能和用户体验已检查；
5. 无调试代码、临时文件和敏感信息；
6. 正式文档和 CHANGELOG 已按当前项目规范更新；
7. Git 差异已检查，功能边界与提交边界一致；
8. 适用的严格或兼容复审已完成，阻塞项已解决；
9. 已按授权提交、推送、部署、重启或在指定位置停止；
10. 所有失败、未验证和遗留风险已明确说明。

如果任务卡明确要求严格独立复审，而工具无法完成，则任务可以是“代码处理和验证已完成，但最终质量门禁受阻”，不得伪称全部完成。

## 九、生产环境操作约束

### 9.1 默认只读

生产默认仅允许查看日志、配置、进程、容器、Pod、端口、资源、监控、Git 状态、中间件状态和只读数据库查询。

修改代码、配置、数据、缓存、消息、文件、Nginx、网络、任务、流量、发布、回滚、重启和扩缩容都需要当前任务明确授权。

### 9.2 前置确认

生产写操作前确认：

- 环境、主机、集群、服务和实例；
- 当前版本、分支、镜像和制品；
- 数据库和中间件目标；
- 流量、影响范围和用户范围；
- 备份、回滚、验收和停止条件。

无法确认环境时不得写入。

### 9.3 高风险操作

`rm -rf`、DROP、TRUNCATE、无条件 DELETE、大范围 UPDATE、FLUSH、Purge、删除索引、对象和 Volume、`git reset --hard`、`git clean`、强推、全部实例重启、关闭鉴权和审计等必须单独说明影响、备份和回滚，并获得明确授权。

### 9.4 生产数据库

执行修改前：

1. 用相同条件执行 SELECT；
2. 确认影响行数；
3. 备份受影响数据；
4. 使用主键或明确索引条件；
5. 准备恢复 SQL；
6. 必要时分批；
7. 每批验证并记录实际影响。

### 9.5 发布和重启

优先单实例、小流量、部分用户、灰度观察、滚动扩大和全量发布。不得默认同时重启全部实例。

重启前检查长任务、事务、未确认消息、SSE、文件传输、优雅停机和摘流。

### 9.6 停止条件

错误率、耗时、资源、连接、慢 SQL、锁等待、消息积压、成功率、用户体验、数据一致性或实际影响超预期时停止扩大，保留现场、收集证据并按既定方案回滚。

### 9.7 操作后验证

验证服务健康、日志、核心接口和页面、数据落库、消息、Redis、文件、SSE、耗时、错误率、资源和数据一致性。

记录操作时间、环境、目标、命令、文件、配置、Commit / 镜像、脚本、影响、验证、回滚和遗留风险。

## 十、Git、CHANGELOG 和交付

### 10.1 提交前检查

检查 `git status`、`git diff`、无关改动、大范围格式化、临时和日志文件、调试代码、敏感信息、锁文件、环境配置和外部记忆文档。

除非明确授权，不推送、不创建 PR、不合并、不强推。

### 10.2 功能边界和提交拆分

一个独立 Bug、功能、接口调整、性能、安全、兼容或迁移通常构成一个功能边界。互不依赖的边界应独立提交。

多个修改只有共同存在才能构成可构建、可验证的完整行为时才可合并，并说明不可拆分原因。

纯提交拆分、提交信息修正和无行为变化的格式修改不是新功能边界。

### 10.3 CHANGELOG

优先遵循当前项目既有规范，例如：

- 每功能提交一条；
- 每 PR 一条；
- 发布时统一维护；
- Conventional Commits、Changesets 或自动生成。

当前项目已有 `CHANGELOG.md` 且任务明确要求按功能边界更新时，应在最终提交前更新，内容必须与实际变更和验证一致。

不得：

- 用 CHANGELOG 替代测试和复审；
- 记录未完成或未验证内容为已完成；
- 把外部任务卡、计划和交接记录写入项目 CHANGELOG；
- 擅自创建与项目规范冲突的新 CHANGELOG。

### 10.4 提交信息

优先项目既有规范。没有明确规范时使用：

```text
<type> |> 中文功能摘要:关键实现与实际验证
```

推荐类型：

- `feat`：新增功能；
- `fix`：Bug 修复；
- `perf`：性能优化；
- `refactor`：不改变对外行为的重构；
- `test`：测试；
- `docs`：文档；
- `chore`：构建、工具和维护；
- `security`：项目允许时用于安全修复。

示例：

```text
fix |> 修复视频任务状态回写:增加幂等校验并完成相关后端定向测试
perf |> 优化订单批量查询:消除循环查询并验证执行计划
feat |> 增加任务取消能力:补充状态流转和接口验证
```

不得使用“优化代码”“修复问题”“更新内容”等无法识别边界的摘要，不得写入未执行的验证。

### 10.5 单功能边界交付顺序

1. 修改；
2. 最低定向验证；
3. 稳定差异；
4. 独立或兼容复审；
5. 修复阻塞项；
6. 重新验证和复审；
7. 更新正式文档或 CHANGELOG；
8. 检查差异；
9. 创建提交并返回真实 Hash；
10. 根据授权停止、推送或继续下一边界。

### 10.6 本地提交但不推送

完成修改、验证、复审、文档和差异检查后创建本地提交，返回真实 Commit Hash，然后停止，禁止推送。

---

## 十一、最终交付格式

复杂任务最终报告按需包含：

### 执行摘要

- 所属项目和执行模式；
- 目标、实际完成和未完成；
- 是否修改代码、配置、数据库和环境；
- 当前提交、推送、部署、重启和生效状态。

### 修改与验证

- 文件和关键改动；
- 实际命令；
- 后端测试、前端构建、Worker、导出、迁移和全量测试结果；
- 失败项、关系判断和未执行原因。

### 独立复审

- 门禁类型；
- Reviewer / 上下文；
- 差异范围；
- 六维结论；
- 阻塞和非阻塞问题；
- 最终结论。

### 影响与状态

- 性能、兼容、安全、权限、用户体验和资源；
- CHANGELOG、提交信息和 Hash；
- 生产制品、重启、版本加载、健康和功能生效层级；
- 风险、未验证项和需要用户执行的操作。

不适用项可省略，但失败、未验证、授权边界和风险不得省略。
