# 技术文档与正式报告编写规则

## 一、目标

技术文档的目标不是堆砌章节，而是让目标读者能够：

1. 准确理解现状、问题、目标和约束；
2. 判断方案是否正确、可落地、可验证和可回滚；
3. 明确实施范围、责任边界、依赖和风险；
4. 在后续开发、测试、部署、运维和审计中复用；
5. 区分已确认事实、推断、计划和未验证项。

文档必须服务于实际决策和执行，不得为了篇幅、形式或“看起来专业”而增加无效内容。

---

## 二、写作前置识别

开始写作或修改前，先识别以下信息。

### 2.1 文档类型

至少判断属于哪一类：

- 技术方案或实施方案；
- 系统或架构设计；
- API 或数据契约设计；
- 数据库、缓存、消息队列或搜索设计；
- 部署、运维、灰度和回滚手册；
- 故障分析、修复报告或复盘；
- 代码审查、性能评估或安全评估；
- 技术选型、可行性评估或方案对比；
- 项目进度、交付说明或管理报告；
- README、开发指南或知识说明；
- 基于已有材料的整理、摘要、重写或格式转换。

### 2.2 目标读者

不同读者需要不同深度和表达方式：

- 开发人员：重视代码边界、接口、数据结构、异常和验证；
- 测试人员：重视验收条件、测试范围、数据准备和回归风险；
- 运维人员：重视部署步骤、配置、监控、停止条件和回滚；
- 架构师或技术负责人：重视边界、权衡、容量、扩展性和成本；
- 产品或业务人员：重视业务目标、流程、影响和验收口径；
- 管理层：重视背景、结论、风险、资源、计划和决策事项；
- 审计或安全人员：重视证据、权限、记录、数据和合规边界。

不得用同一种技术细节密度机械服务所有读者。

### 2.3 文档用途

明确文档用于：

- 讨论和决策；
- 开发实施；
- 评审和验收；
- 上线审批；
- 生产操作；
- 事故复盘；
- 工作交接；
- 培训和知识沉淀；
- 对外或跨部门沟通。

用途决定是否需要版本、审批、操作步骤、回滚、证据和附件。

### 2.4 交付边界

确认：

- 输出 Markdown、DOCX、PDF、网页还是纯文本；
- 新建文档还是修改现有文档；
- 是否允许写入仓库；
- 是否需要更新目录、索引、README 或 CHANGELOG；
- 是否需要图表、Mermaid、表格或附件；
- 是否需要遵循公司、项目或用户现有模板；
- 是否需要本地提交、推送或发布。

没有相应授权时，只能提供内容或建议，不能擅自写入、覆盖、提交或发布。

## 三、事实来源与证据管理

### 3.1 事实来源优先级

技术事实优先级通常为：

1. 实际运行结果、测试、监控和可复现证据；
2. 当前代码、配置、数据库结构和制品；
3. 当前日志、数据库状态、中间件状态和命令结果；
4. 当前 Git 状态、Commit 和差异；
5. 项目正式接口契约、迁移记录和现行文档；
6. 用户明确确认的项目事实；
7. 历史资料和通用工程经验。

当来源冲突时，明确列出冲突，不得静默选择更方便的结论。

### 3.2 基于用户材料写作

用户要求基于附件、代码、日志或现有文档进行整理时：

- 将这些材料作为主要依据；
- 保留原有术语、业务口径、组织逻辑和细节层级；
- 不自行替换为更熟悉但不同的业务概念；
- 不静默修正原文中的事实、数字和结论；
- 发现明显冲突或错误时，单独标记“待确认”或“建议修正”；
- 材料没有覆盖的内容，明确写“现有材料未说明”；
- 用户要求扩展、核验或外部研究时，将来源内结论与外部补充清楚分开。

### 3.3 证据等级

文档中的关键结论按需标记：

- **已确认**：有直接代码、配置、日志、测试、监控或执行证据；
- **高概率**：有较强证据，但尚未完整复现或闭环；
- **推断**：基于工程逻辑和现有线索推导；
- **假设**：为推进方案暂时采用的前提；
- **未验证**：当前无法验证；
- **待确认**：必须由用户、业务或环境负责人确认。

计划、目标和建议不能写成已经发生的事实。

### 3.4 禁止虚假证据

不得编造：

- 测试通过、构建成功、压测结果和性能收益；
- 代码路径、接口、字段、配置、表结构和版本；
- Commit、发布时间、部署状态和生产恢复结果；
- 用户数量、并发量、工期、预算和资源投入；
- 事故原因、责任主体和业务影响；
- 会议结论、审批状态和人员承诺。

没有证据时使用范围明确的条件表达，不使用“确保”“完全解决”“无影响”等绝对措辞。

## 四、结构设计原则

### 4.1 最小充分结构

文档结构应覆盖当前用途所需信息，但不机械套用所有章节。

常见基础结构：

1. 摘要或执行摘要；
2. 背景和现状；
3. 问题与目标；
4. 范围和非目标；
5. 方案或分析；
6. 影响和风险；
7. 实施或验证；
8. 回滚、监控和验收；
9. 未验证项和后续事项。

简单说明可以只有背景、结论和操作步骤；生产方案则必须补充风险、停止条件、回滚和验证。

### 4.2 标题层级

- 一级标题只表达文档主题；
- 二级标题表达主要决策或工作阶段；
- 三级标题表达同一章节下的具体问题；
- 避免标题层级跳跃；
- 避免一个标题下只有一句话；
- 避免大量同级小标题造成文档碎片化。

### 4.3 摘要

摘要应快速回答：

- 为什么需要这份文档；
- 当前最重要的事实是什么；
- 推荐或结论是什么；
- 影响和主要风险是什么；
- 下一步需要做什么或决定什么。

摘要不能引入正文没有说明的新结论。

### 4.4 范围和非目标

复杂任务必须说明：

- 本次覆盖的系统、模块、环境和数据；
- 明确不处理的事项；
- 依赖的前提和外部系统；
- 不允许改变的接口、业务口径或历史兼容逻辑。

这样可以防止文档被误解为更大范围的授权或承诺。

## 五、语言和表达

### 5.1 默认风格

默认使用：

- 中文；
- 正式、专业、中立；
- 直接、具体、可落地；
- 以事实和决策为中心；
- 使用当前领域的准确术语；
- 避免口号、情绪化和营销式表达。

### 5.2 避免模糊措辞

避免单独使用：

- “进行优化”；
- “提升性能”；
- “完善功能”；
- “解决问题”；
- “保证稳定”；
- “用户体验更好”；
- “按需处理”；
- “后续关注”。

应说明优化对象、实施动作、验证方式和边界。例如：

> 将循环内逐条查询改为一次批量查询，并通过相关接口定向测试和 SQL 执行计划验证查询数量与索引使用情况。

### 5.3 中立表达

涉及组织、人员、责任和评估时：

- 描述事实、流程和影响，不进行情绪化归因；
- 未经证据不判断责任；
- 区分系统原因、流程原因、配置原因和人为操作；
- 建议使用“当前方案”“现有实现”“本次范围”，避免贬低性用语。

### 5.4 技术术语

- 首次出现的缩写按需给出全称或简要说明；
- 项目已有术语优先于通用替代术语；
- 同一概念在全文使用统一名称；
- Java、Python、数据库、消息队列和 AI 术语不得混用或误用。

## 六、表格、列表、代码和图

### 6.1 表格

适合使用表格的场景：

- 多方案对比；
- 模块职责和边界；
- 接口字段和数据库字段；
- 风险矩阵；
- 阶段、里程碑和验收条件；
- 环境、配置和部署差异；
- 测试结果和证据清单。

表格列数过多或单元格内容过长时，改用分节说明，避免横向难读。

### 6.2 列表

- 列表项保持同一语法和粒度；
- 每一项表达一个完整动作或判断；
- 有顺序依赖时使用编号列表；
- 无顺序分类使用项目符号；
- 不用层层嵌套列表代替正常段落。

### 6.3 代码和命令

代码、SQL、配置和命令必须：

- 与当前版本和环境匹配；
- 使用正确语言标识的代码块；
- 说明执行环境、前置条件和风险；
- 对生产写操作给出查询、备份、影响范围和回滚；
- 不包含真实密码、Token、密钥、Cookie 和隐私数据；
- 不把示例命令描述为已经执行。

### 6.4 Mermaid

适合展示：

- 系统架构；
- 服务调用链；
- 业务流程；
- 状态机；
- 时序交互；
- 部署拓扑；
- 数据流。

要求：

- 节点名称与正文一致；
- 标明系统边界和外部依赖；
- 不添加材料中不存在的服务；
- 复杂图拆分为多张单一主题图；
- 图后补充关键链路和异常路径说明；
- 保证 Mermaid 语法可解析。

## 七、不同文档的关键要求

### 7.1 技术方案

至少回答：

- 现状和根因是什么；
- 目标和非目标是什么；
- 有哪些候选方案；
- 推荐方案为什么适合当前阶段；
- 对接口、数据、性能、安全和兼容有什么影响；
- 如何实施、验证、灰度和回滚；
- 什么条件下需要升级方案。

### 7.2 架构设计

至少明确：

- 业务和系统边界；
- 模块或服务职责；
- 数据所有权；
- 同步和异步交互；
- 事务和一致性边界；
- 容量、扩缩容和故障隔离；
- 权限、安全、可观测性和部署；
- 成本和演进路线。

### 7.3 实施计划

每个阶段应包含：

- 目标；
- 输入和前置条件；
- 修改范围；
- 输出；
- 验证；
- 风险；
- 停止条件；
- 回滚点；
- 依赖关系。

不能把尚未确认的日期和人员写成确定承诺。

### 7.4 API 设计

至少明确：

- 接口用途、调用方和权限；
- 路径、方法、版本和幂等；
- 请求、响应、错误码和示例；
- 字段含义、类型、必填、长度、枚举、精度和时区；
- 分页、排序、过滤和批量上限；
- 兼容策略、限流、超时和审计；
- 敏感字段和数据权限。

### 7.5 数据库设计

至少明确：

- 业务对象和数据所有权；
- 表、字段、类型、默认值和约束；
- 主键、唯一约束和索引；
- 查询模式和执行计划考虑；
- 事务、锁、并发和幂等；
- 历史数据、迁移、新旧代码共存和回滚；
- 数据保留、归档和审计。

### 7.6 部署与运维文档

必须区分：

- 环境和目标实例；
- 前置检查；
- 制品、配置和密钥；
- 部署步骤；
- 数据库和中间件操作；
- 健康检查和业务验收；
- 监控指标和观察期；
- 停止条件和回滚步骤；
- 操作记录。

命令成功不等于功能生效。

### 7.7 故障报告

按证据区分：

- 现象和影响；
- 时间线；
- 已知证据；
- 可能原因和验证过程；
- 已确认根因；
- 临时止血；
- 正式修复；
- 恢复验证；
- 防复发措施；
- 未验证项和后续观察。

根因未确认时，不得为了完整性强行给出唯一根因。

### 7.8 代码审查报告

建议包含：

- 功能理解；
- 审查范围和基线；
- Bug、空指针、并发、事务、SQL、性能、安全、兼容和维护性问题；
- 每个问题的证据、等级、影响和建议；
- 阻塞项和非阻塞项；
- 未阅读或未验证范围；
- 最终结论。

### 7.9 进度和交付报告

必须区分：

- 已完成；
- 进行中；
- 未开始；
- 受阻；
- 已验证；
- 未验证；
- 已提交、已推送、已部署、已重启和已生效。

不得只写“优化完成”，应列出实际交付、验证证据和遗留风险。

### 7.10 面向管理层的报告

优先表达：

- 业务背景和目标；
- 当前状态；
- 核心结论；
- 影响范围；
- 方案和资源；
- 风险和控制；
- 计划和决策事项。

保留必要技术依据，但避免无助于决策的大段源码和底层细节。

## 八、多方案对比

多个方案至少比较：

| 维度 | 说明 |
|---|---|
| 业务适配 | 是否满足当前需求和口径 |
| 实现成本 | 开发、测试、迁移和培训成本 |
| 上线风险 | 变更范围、停机、数据和回滚风险 |
| 性能与容量 | 延迟、吞吐、资源和扩展能力 |
| 兼容性 | 旧接口、旧数据和新旧版本共存 |
| 安全 | 权限、数据和供应链风险 |
| 可维护性 | 复杂度、可观测性和团队能力 |
| 运维成本 | 部署、监控、故障和资源成本 |
| 回滚难度 | 是否能快速恢复原链路 |
| 适用阶段 | PoC、初期、增长期或成熟期 |

对比后必须给出：

- 推荐方案；
- 推荐理由；
- 不推荐其他方案的原因；
- 适用前提；
- 重新评估或升级条件。

---

## 九、现有文档修改规则

修改已有文档时：

1. 阅读完整文档和相关上下文；
2. 明确目标修改范围；
3. 保留原有标题、编号、链接、术语和未修改内容；
4. 不顺手重写无关章节；
5. 检查目录、锚点、交叉引用和版本信息；
6. 发现历史错误但不在范围内时，记录为待确认或额外发现；
7. 修改后检查前后定义、数字、状态和结论是否一致；
8. 需要覆盖原文件、进入 Git 或发布时遵循当前授权。

若用户明确要求“全面重构”，可以调整结构，但仍应保留有效事实、业务口径和可追溯信息。

---

## 十、正式文档与 Agent 外部记忆的隔离

正式工程文档可能进入项目仓库并供团队使用，例如：

- 架构文档；
- 接口文档；
- 部署手册；
- 数据库设计；
- 技术方案；
- 项目 README；
- 正式 CHANGELOG。

Agent 外部记忆仅用于任务恢复，例如：

- `CURRENT_TASK.md`；
- `PLAN.md`；
- `PROGRESS.md`；
- `HANDOFF.md`；
- `DELIVERY_RECORD.md`。

除非项目明确采用这些文件作为正式规范，否则外部记忆不得进入项目仓库、Git 或正式 CHANGELOG。

## 十一、文档质量复核

交付前至少检查以下维度。

### 11.1 准确性

- 事实是否有来源；
- 术语、版本、接口、字段和状态是否准确；
- 是否把推断或计划写成事实；
- 数字和结论是否前后一致。

### 11.2 完整性

- 是否覆盖目标读者真正需要的信息；
- 是否遗漏异常、兼容、权限、回滚和验证；
- 是否明确未验证项和依赖。

### 11.3 一致性

- 标题、编号、名称、状态和时间是否统一；
- 图、表和正文是否一致；
- 文档与代码、配置、测试和 CHANGELOG 是否一致。

### 11.4 可执行性

- 实施步骤是否有前置条件、输入、输出和验证；
- 操作命令是否有环境、权限和风险说明；
- 是否有停止条件和回滚。

### 11.5 可维护性

- 是否记录版本、日期和适用范围；
- 是否避免复制大量易过时源码；
- 是否便于后续更新和检索；
- 是否避免不必要的重复章节。

### 11.6 安全性

- 是否包含密码、Token、密钥、Cookie、隐私或企业敏感信息；
- 是否提供未经授权的生产写操作；
- 是否暴露内部地址、账号和真实数据；
- 示例是否已经脱敏。

### 11.7 可读性

- 摘要是否能够快速传达结论；
- 章节是否围绕一个明确主题；
- 表格、列表和图是否真正帮助理解；
- 技术深度是否适合目标读者。

## 十二、最终交付

完成后根据任务复杂度说明：

- 文档名称和用途；
- 主要依据；
- 新建或修改的文件；
- 关键结论；
- 已确认、假设和未验证项；
- 是否写入仓库、提交、推送或发布；
- 仍需用户确认的事项。

简单文档不需要机械输出完整交付报告，但不能隐瞒来源不足、未验证或实际未生成的文件。
