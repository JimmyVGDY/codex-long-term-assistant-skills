## 九、现有文档修改规则

修改已有文档时：

1. 阅读完整文档和相关上下文；
2. 明确目标修改范围；
3. 保留原有标题、编号、链接、术语和未修改内容；
4. 不顺手重写无关章节；
5. 检查目录、锚点、交叉引用和版本信息；
6. 发现历史错误但不在范围内时，记录为待确认或额外发现；
7. 修改后检查前后定义、数字、状态和结论是否一致；
8. 需要覆盖原文件、进入 Git 或发布时遵循当前授权。

若用户明确要求“全面重构”，可以调整结构，但仍应保留有效事实、业务口径和可追溯信息。

## 十、正式文档与 Agent 外部记忆的隔离

正式工程文档可能进入项目仓库并供团队使用，例如：

- 架构文档；
- 接口文档；
- 部署手册；
- 数据库设计；
- 技术方案；
- 项目 README；
- 正式 CHANGELOG。

Agent 外部记忆仅用于任务恢复，例如：

- `CURRENT_TASK.md`；
- `PLAN.md`；
- `PROGRESS.md`；
- `HANDOFF.md`；
- `DELIVERY_RECORD.md`。

除非项目明确采用这些文件作为正式规范，否则外部记忆不得进入项目仓库、Git 或正式 CHANGELOG。

## 十一、文档质量复核

交付前至少检查以下维度。

### 11.1 准确性

- 事实是否有来源；
- 术语、版本、接口、字段和状态是否准确；
- 是否把推断或计划写成事实；
- 数字和结论是否前后一致。

### 11.2 完整性

- 是否覆盖目标读者真正需要的信息；
- 是否遗漏异常、兼容、权限、回滚和验证；
- 是否明确未验证项和依赖。

### 11.3 一致性

- 标题、编号、名称、状态和时间是否统一；
- 图、表和正文是否一致；
- 文档与代码、配置、测试和 CHANGELOG 是否一致。

### 11.4 可执行性

- 实施步骤是否有前置条件、输入、输出和验证；
- 操作命令是否有环境、权限和风险说明；
- 是否有停止条件和回滚。

### 11.5 可维护性

- 是否记录版本、日期和适用范围；
- 是否避免复制大量易过时源码；
- 是否便于后续更新和检索；
- 是否避免不必要的重复章节。

### 11.6 安全性

- 是否包含密码、Token、密钥、Cookie、隐私或企业敏感信息；
- 是否提供未经授权的生产写操作；
- 是否暴露内部地址、账号和真实数据；
- 示例是否已经脱敏。

### 11.7 可读性

- 摘要是否能够快速传达结论；
- 章节是否围绕一个明确主题；
- 表格、列表和图是否真正帮助理解；
- 技术深度是否适合目标读者。

## 十二、最终交付

完成后根据任务复杂度说明：

- 文档名称和用途；
- 主要依据；
- 新建或修改的文件；
- 关键结论；
- 已确认、假设和未验证项；
- 是否写入仓库、提交、推送或发布；
- 仍需用户确认的事项。

简单文档不需要机械输出完整交付报告，但不能隐瞒来源不足、未验证或实际未生成的文件。
