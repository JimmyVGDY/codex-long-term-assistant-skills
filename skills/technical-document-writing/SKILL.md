# 技术文档与正式报告编写技能

## 使用范围

用于从代码、配置、日志、数据库结构、测试结果、项目资料和用户要求中形成可审查、可执行、可交付的技术文档或正式报告。

适用文档包括但不限于：

- 技术方案、架构设计和系统设计；
- 实施计划、迁移方案、灰度与回滚方案；
- API、数据库、缓存、消息队列和部署设计；
- 故障分析、修复报告、代码审查和性能评估；
- 技术选型、可行性分析和多方案对比；
- 项目进度、交付说明、团队协作和面向管理层的正式报告；
- README、开发指南、运维手册和现有 Markdown 文档重构。

## 执行步骤

1. 开始写作或改写前，读取 `references/technical-document-writing-rules.md`。
2. 根据任务类型按需读取 `references/document-type-playbooks.md`，不要无条件加载所有模板。
3. 明确文档的目标读者、用途、决策问题、事实来源、交付格式、详细程度和修改权限。
4. 如果用户提供了文件、代码或资料，以这些材料为主要依据，保留其术语、业务口径、组织方式和细节层级；材料未支持的结论不得静默补齐。
5. 区分已确认事实、外部资料、工程推断、假设和未验证项。不能把计划写成已完成，也不能把静态分析写成运行验证。
6. 从 `assets/templates/` 选择最接近的模板并按实际任务裁剪；简单文档不得机械套用全部章节。
7. 需要技术细节时，同时使用当前领域对应技能，例如 Java、Python、Vue 或数据基础设施技能；基于日志编写故障报告、复盘或时间线时组合 `$log-observability-analysis`。
8. 文档与代码修改、测试、CHANGELOG、提交或发布绑定时，同时使用 `$engineering-quality-delivery`。
9. 跨会话计划、进度、决策和交接属于 Agent 外部工作记忆时，使用 `$long-running-task-memory`，不要把这些内部记录混入正式项目文档。
10. 写入现有文档前先阅读完整上下文，保留未要求修改的内容、原有风格、标题层级、链接和编号。
11. 完成后执行文档质量复核：准确性、完整性、一致性、可执行性、可维护性、安全性和读者可读性。

## 默认输出规则

- 默认使用中文和 Markdown；用户或项目规范另有要求时遵循实际格式。
- 语言正式、专业、中立，不夸大，不使用未经验证的绝对结论。
- 技术方案优先给出明确推荐、适用条件、成本、风险、验证和回滚。
- 架构图优先使用可维护的 Mermaid，但图中组件、链路和边界必须有事实依据。
- 表格用于对比、矩阵、字段和阶段信息；普通说明不要为了形式全部表格化。
- 文档需要进入仓库、覆盖原文件、生成 Word/PDF 或提交 Git 时，必须具备对应授权和工具能力。

## 边界

- 不编造项目现状、代码行为、版本、测试结果、性能数据、工期、预算、人员职责或生产状态。
- 不因“写一份完整文档”而擅自修改代码、配置、数据库、Git 或环境。
- 不把 Agent 外部记忆文档当成团队正式工程文档。
- 不把 CHANGELOG、Commit 信息和代码注释的简单更新扩大成完整文档任务。
- 不声称已经生成 DOCX、PDF、图表或附件，除非实际文件已经创建并验证。
