# 数据、中间件、AI 与基础设施工程规则

> 当前任务涉及数据库、Redis、消息队列、搜索、文件存储、AI、RAG、GPU、微服务、可观测性、Docker 或 Kubernetes 时按需加载。语言模块只补充客户端特有问题，本文件定义跨语言公共规则。

## 一、接口、数据和契约兼容

涉及 API、数据库、消息、缓存、文件和序列化时，必须检查契约兼容。

未经明确要求不得：

- 删除已有字段或修改字段含义、类型和默认值；
- 修改已有枚举、状态、错误码和异常语义；
- 修改消息格式、Redis Key、对象 Key 和序列化格式；
- 破坏历史数据、旧调用方、旧前端、旧 Worker 和旧实例；
- 在灰度期间制造新旧版本不能共存的双向不兼容。

新增字段应让旧调用方可以忽略。消息消费者、缓存反序列化和数据库迁移要考虑新旧格式共存。

契约变化必须说明：

- 生产者、消费者和数据所有者；
- 新旧版本兼容窗口；
- 默认值和降级行为；
- 数据迁移、回滚和清理计划；
- 灰度和监控指标。

## 二、数据库与 SQL

### 2.1 查询和索引

主动检查：

- 索引命中、联合索引最左匹配和覆盖索引；
- 回表、全表扫描、文件排序和临时表；
- 深分页、N+1、相关子查询和重复查询；
- 批量操作、唯一约束和幂等；
- 数据倾斜、统计信息和执行计划；
- 主从延迟和读写一致性。

给出 SQL 时说明推荐索引、字段顺序、预计影响行数、锁范围、执行计划验证、回滚方式和是否适合生产直接执行。

禁止为了“可能更快”盲目增加索引。必须评估写放大、存储、选择性和已有索引冗余。

### 2.2 事务、锁和一致性

检查隔离级别、行锁、间隙锁、死锁、锁等待、长事务、事务重试和跨系统一致性。

不得在数据库事务中长期执行外部调用、文件处理和人工等待。关键写入优先使用数据库唯一约束、版本号、状态条件和受控重试保证幂等。

涉及“先查后改”时检查竞态，必要时使用：

- 唯一约束；
- 条件更新；
- 乐观锁；
- 悲观锁；
- 幂等表；
- Outbox 或最终一致性方案。

### 2.3 DDL 和数据迁移

评估锁表、表重建、在线 DDL、新旧代码共存、数据回填、主从复制和磁盘空间。

大表变更优先拆分：

1. 添加兼容结构；
2. 发布兼容代码；
3. 分批回填；
4. 切换读写；
5. 验证和观察；
6. 最后清理旧结构。

已执行历史迁移不得修改，使用增量脚本。数据回填支持限速、重试、断点、审计和补偿。

## 三、Redis

主动分析：

- 缓存穿透、击穿、雪崩和热点 Key；
- 大 Key、TTL、随机过期、预热和淘汰策略；
- 双写一致性、延迟双删、失效顺序和缓存污染；
- Cluster 槽位、主从切换和多实例一致性；
- Session、幂等、限流和任务状态；
- 序列化版本兼容。

### 3.1 Key 和 Value

Key 必须有项目、环境、业务域和版本边界，避免跨项目和跨环境冲突。Value 大小、集合元素数量和 TTL 必须有上限。

### 3.2 分布式锁

明确锁 Key、持有者标识、超时、续期、解锁所有权、失败处理、锁内耗时和降级策略。

不得在锁内执行长时间远程调用、大文件处理和不可控等待。解锁必须校验所有权，防止误删他人锁。

### 3.3 生产操作

生产禁止直接使用：

```text
KEYS *
FLUSHALL
FLUSHDB
```

查询使用 `SCAN`。删除前确认数量、Value 大小、是否 Session、锁、任务状态、幂等和限流数据，以及删除后的击穿和恢复风险。

## 四、RabbitMQ、Celery 和消息队列

主动检查：

- 生产者确认、Return、持久化和路由失败；
- 消费者 ACK、Prefetch、并发和连接恢复；
- 消息丢失、重复消费、幂等和顺序性；
- 重试、退避、死信、Poison Message 和最终失败；
- 消息堆积、消费者限流、任务超时和取消；
- 网络抖动、多实例竞争和消息版本兼容。

### 4.1 成功边界

ACK 时机必须与业务成功边界一致。不能业务未提交就 ACK，也不能业务已成功却因响应异常反复重做。

### 4.2 幂等

幂等不能只依赖消费者进程内变量。根据场景使用：

- 数据库唯一约束；
- 幂等记录；
- 状态条件更新；
- 业务版本号；
- 可重放的状态机。

### 4.3 重试

说明最大次数、间隔、指数退避、可重试异常、不可重试异常和最终失败处理。

禁止对参数错误、业务拒绝和永久性错误无限重试。防止多层重试、重试风暴和下游压力放大。

### 4.4 顺序

需要顺序时明确顺序范围：全局、业务主键、分区或单消费者。必须评估并发、重试和死信重放对顺序的破坏。

### 4.5 生产操作

未经明确授权不得 Purge Queue、删除 Queue / Exchange、取消全部消费者、重放全部死信和大规模重新投递。重放前必须验证消费者幂等和容量。

## 五、Elasticsearch、搜索和向量数据库

### 5.1 Elasticsearch

检查：

- Mapping、字段类型、分词器和动态映射；
- Keyword / Text、日期、数值和嵌套对象；
- 分片、副本、刷新、段合并和磁盘水位；
- 查询 DSL、深分页、聚合、排序和脚本；
- 索引模板、别名、ILM 和滚动索引；
- 批量写入、版本冲突和重试；
- 权限、敏感字段和多租户隔离。

避免无边界通配符、前导通配符、超大 `size`、深度 `from + size` 和高基数聚合。深分页评估 `search_after` 或 Scroll 的适用边界。

索引重建优先新索引 + 别名切换，保留回滚别名。删除索引属于高风险操作。

### 5.2 向量数据库

检查向量维度、距离算法、索引类型、过滤条件、多租户、批量写入、删除、重建、版本和成本。

Embedding 模型变化通常意味着向量不可直接兼容，需要版本化索引和重建方案。

## 六、文件、NAS、对象存储和 CDN

主动考虑：

- 文件一致性、元数据状态和数据所有权；
- 对象 Key、上传幂等、重复文件和校验；
- 分片、断点、限速、超时、失败重试和取消；
- 全量迁移、增量同步、灰度切读写和回滚；
- CDN 缓存、刷新、版本 URL 和旧资源兼容；
- NAS 重 I/O、大目录遍历、大文件和小文件问题；
- 线程池、进程和 Worker 隔离；
- 临时文件、磁盘空间、清理和存储成本。

### 6.1 一致性模型

必须明确：

- 数据库元数据与文件对象谁是事实源；
- 上传成功、元数据提交和消息发送的顺序；
- 部分成功和失败补偿；
- 删除是软删除、延迟删除还是立即删除；
- 同步任务如何幂等和断点恢复。

### 6.2 安全

检查路径穿越、越权下载、签名 URL、MIME、扩展名、文件签名、恶意文件、目录逃逸和对象 Key 注入。

不得信任用户文件名作为物理路径。生产删除对象和目录必须先确认范围和恢复能力。

### 6.3 NAS 资源控制

大目录遍历、索引刷新、递归删除和批量校验属于重 I/O。应通过任务队列、并发上限、优先级和速率控制保护共享存储，但不能简单把所有普通读取串行化。

---

## 七、SSE、WebSocket 和流式链路

跨前后端检查：

- 连接建立、心跳、超时、关闭和重连；
- 客户端断开、服务端取消和下游任务取消；
- 消息顺序、重复、半截消息和最后事件位置；
- 数据落库、上下文保存和刷新恢复；
- 多实例路由、粘性会话、广播和网关缓冲；
- 页面切换、浏览器休眠和资源释放；
- 任务状态与展示状态最终一致。

不得只修复连接表现而忽略消息落库、上下文、任务状态、泄漏和恢复。

---

## 八、AI、RAG、模型和 GPU

### 8.1 AI 调用

主动分析：

- 模型能力和使用边界；
- Prompt、System Prompt、上下文窗口和 Token 成本；
- JSON Schema、结构化输出、校验和修复；
- Prompt 注入、敏感信息和工具权限；
- 超时、重试、降级、多模型路由和缓存；
- 幂等、取消、失败恢复和链路追踪。

不得把模型输出直接视为可信业务数据。涉及金额、权限、状态和执行命令时必须程序化校验。

### 8.2 RAG

检查：

- 文档解析、Chunk 大小、重叠和 Metadata；
- Embedding 模型、向量维度和版本；
- TopK、BM25、混合检索、RRF、Rerank 和 MMR；
- 权限过滤、多租户和敏感文档；
- 数据更新、删除、重建和索引一致性；
- 评测集、召回、准确性、幻觉和引用。

RAG 评测不能只看主观示例，应建立真实问题、期望证据和可重复指标。

### 8.3 Agent 和工具调用

明确工具权限、输入 Schema、超时、幂等、重试、人工确认和审计。工具返回必须校验，不得让模型自由拼接高风险命令或 SQL 并直接执行。

### 8.4 GPU 和视频任务

检查显存、模型常驻、同卡竞争、Worker 并发、队列、优先级、OOM、批处理、取消、恢复、Worker 崩溃、中间产物、文件清理和 GPU 利用率。

GPU 任务需要资源预算和调度策略，不能只通过增加并发提升吞吐。必须同时评估 CPU、内存、磁盘、网络和模型加载开销。

---

## 九、微服务和服务拆分

不得因为性能问题直接建议拆微服务。先定位 SQL、缓存、阻塞、连接池、线程池、单进程限制、文件 I/O、CPU、GPU、外部接口和任务异步化。

拆分依据：

- 业务、数据和事务边界；
- 发布独立性和故障隔离；
- 资源类型和扩缩容；
- 团队组织、运维成本和网络开销；
- 数据一致性和可观测性成本。

早期和小型项目优先模块化单体 + 独立 Worker。常见合理拆分包括 Web API、普通 Worker、文件 Worker、视频 Worker、AI Worker、GPU Worker 和调度服务。

服务间必须统一 traceId、错误码、超时、重试、幂等和版本策略，避免循环依赖和多层重试。

## 十、安全、权限和供应链

### 10.1 敏感信息

代码、配置、日志和文档中脱敏密码、Token、AccessKey、SecretKey、Cookie、Session、身份证、手机号、银行卡、地址和企业敏感信息。

使用明确占位符：

```text
<YOUR_TOKEN>
<YOUR_PASSWORD>
<YOUR_ACCESS_KEY>
<YOUR_SECRET_KEY>
```

### 10.2 权限

检查认证、接口权限、数据权限、租户隔离、水平和垂直越权、ID 枚举、越权下载和修改、管理接口和审计日志。

不能依赖前端隐藏按钮。新接口、异步入口、回调、文件和任务状态查询都必须检查资源归属。

### 10.3 常见攻击面

检查 SQL 注入、命令注入、SSRF、路径穿越、XSS、CSRF、反序列化、模板和表达式注入、XXE、开放重定向、日志注入、不安全上传和下载。

### 10.4 供应链

引入或升级依赖、镜像和脚本时检查官方来源、版本兼容、传递依赖、CVE、License、默认行为、回退和同名仿冒包。

未经明确要求不执行来源不明脚本、不使用来源不明镜像、不引入维护状态不明依赖。

## 十一、可观测性、资源预算和功能开关

### 11.1 可观测性

核心链路记录 traceId、requestId、taskId、messageId、脱敏业务标识、状态、耗时、重试、失败原因、服务和 Worker。

指标至少考虑：

- 请求量、错误率、P95/P99；
- CPU、内存、GC、线程、协程和进程；
- 数据库和 Redis 连接；
- 队列长度、消息积压和任务耗时；
- 文件 I/O、磁盘、NAS 和对象存储；
- Token、模型延迟、GPU 显存和利用率。

日志必须可定位、可关联、不泄密、不吞异常、不在高频路径输出大量内容。

### 11.2 资源预算

设计和修改时评估：

- 最大并发、队列长度和单任务内存；
- 线程池、协程、进程和 Worker 数量；
- 数据库、Redis 和 HTTP 连接池；
- MQ Prefetch；
- 文件大小和上传下载速率；
- 请求超时、重试总时长和 Token；
- GPU 显存和模型常驻。

禁止无限队列、无限并发、无限重试、无上限文件和无超时调用。

### 11.3 功能开关

高风险和核心链路改动优先考虑 Feature Flag、配置开关、租户或用户灰度、流量比例和新旧链路切换。

明确默认值、作用范围、关闭路径、监控指标、回滚和后续清理。功能开关不能永久堆积形成不可维护分支。

---

## 十二、Docker、Kubernetes 和运行环境

### 12.1 Docker

检查：

- 基础镜像来源、版本和漏洞；
- 多阶段构建、非 root 用户和最小权限；
- 镜像体积、构建缓存和可复现性；
- 环境变量、Secret、挂载目录和只读文件系统；
- 健康检查、优雅停止、日志和时区；
- CPU、内存、磁盘和 GPU 限制；
- 临时文件和持久化卷边界。

不得把密钥写入镜像层或提交到仓库。不要在运行容器中临时修改后当作正式交付。

### 12.2 Kubernetes

检查 Deployment / StatefulSet / Job / CronJob 选择，Requests / Limits，Probe，滚动发布，PDB，HPA，亲和性，Secret，ConfigMap，Service 和 Ingress。

防止：

- Readiness 未通过就接流量；
- Liveness 过于激进造成重启风暴；
- 滚动更新同时停止全部实例；
- Job 重试导致重复业务；
- 配置刷新和版本不一致；
- 临时盘不足、OOMKilled 和节点资源争抢。

### 12.3 网络和代理

检查 DNS、超时、Keep-Alive、代理、Nginx 缓冲、上传限制、WebSocket/SSE 转发、TLS 和防火墙。网络故障必须区分客户端、代理、容器、主机、DNS 和下游服务。
