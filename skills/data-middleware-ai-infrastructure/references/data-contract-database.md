# 数据契约、关系数据库、事务与迁移

## 一、接口、数据和契约兼容

涉及 API、数据库、消息、缓存、文件和序列化时，必须检查契约兼容。

未经明确要求不得：

- 删除已有字段或修改字段含义、类型和默认值；
- 修改已有枚举、状态、错误码和异常语义；
- 修改消息格式、Redis Key、对象 Key 和序列化格式；
- 破坏历史数据、旧调用方、旧前端、旧 Worker 和旧实例；
- 在灰度期间制造新旧版本不能共存的双向不兼容。

新增字段应让旧调用方可以忽略。消息消费者、缓存反序列化和数据库迁移要考虑新旧格式共存。

契约变化必须说明：

- 生产者、消费者和数据所有者；
- 新旧版本兼容窗口；
- 默认值和降级行为；
- 数据迁移、回滚和清理计划；
- 灰度和监控指标。

## 二、数据库与 SQL

### 2.1 查询和索引

主动检查：

- 索引命中、联合索引最左匹配和覆盖索引；
- 回表、全表扫描、文件排序和临时表；
- 深分页、N+1、相关子查询和重复查询；
- 批量操作、唯一约束和幂等；
- 数据倾斜、统计信息和执行计划；
- 主从延迟和读写一致性。

给出 SQL 时说明推荐索引、字段顺序、预计影响行数、锁范围、执行计划验证、回滚方式和是否适合生产直接执行。

禁止为了“可能更快”盲目增加索引。必须评估写放大、存储、选择性和已有索引冗余。

### 2.2 事务、锁和一致性

检查隔离级别、行锁、间隙锁、死锁、锁等待、长事务、事务重试和跨系统一致性。

不得在数据库事务中长期执行外部调用、文件处理和人工等待。关键写入优先使用数据库唯一约束、版本号、状态条件和受控重试保证幂等。

涉及“先查后改”时检查竞态，必要时使用：

- 唯一约束；
- 条件更新；
- 乐观锁；
- 悲观锁；
- 幂等表；
- Outbox 或最终一致性方案。

### 2.3 DDL 和数据迁移

评估锁表、表重建、在线 DDL、新旧代码共存、数据回填、主从复制和磁盘空间。

大表变更优先拆分：

1. 添加兼容结构；
2. 发布兼容代码；
3. 分批回填；
4. 切换读写；
5. 验证和观察；
6. 最后清理旧结构。

已执行历史迁移不得修改，使用增量脚本。数据回填支持限速、重试、断点、审计和补偿。
