# 长期任务外部记忆与文档维护机制

> 仅在跨会话、多阶段、多模块、多仓库、多 Agent、生产风险或上下文可能压缩的任务中加载。简单任务不得为了形式创建全部文档。

## 一、目标和边界

长期任务不得完全依赖聊天上下文保存状态。应使用 Agent 可访问的本机专用目录记录可验证事实、授权、计划、进度、决策、复审和交付证据。

外部记忆只保存工作恢复所需的事实和状态，不保存冗长内部推理、无关工具输出和未经验证的猜测。

外部记忆不能覆盖当前实际代码、配置、Git 和运行结果，也不能作为任务完成证据的替代品。

---

## 二、目录约定

根目录使用可配置占位符：

```text
<AGENT_CONTEXT_ROOT>/<项目标识>/
```

`<AGENT_CONTEXT_ROOT>` 由当前机器、Agent 或项目级配置确定，例如 Windows、WSL、Linux 和其他工具可以使用不同路径。

禁止在全局规则中写死用户名、操作系统路径和某个具体项目目录。

推荐结构：

```text
<AGENT_CONTEXT_ROOT>/<项目标识>/
├── PROJECT_CONTEXT.md
├── CURRENT_TASK.md
├── PLAN.md
├── PROGRESS.md
├── DECISIONS.md
├── HANDOFF.md
├── KNOWN_ISSUES.md
├── DELIVERY_RECORD.md
└── archive/
```

---

## 三、文档职责

| 文档 | 作用 | 默认触发 |
|---|---|---|
| `PROJECT_CONTEXT.md` | 长期稳定的项目事实、技术栈和约束 | 复杂项目建议存在 |
| `CURRENT_TASK.md` | 当前目标、范围、授权和验收 | 复杂任务 |
| `PLAN.md` | 阶段、依赖、风险、验证和复审计划 | 多步骤任务 |
| `PROGRESS.md` | 实际修改、命令、测试、复审和阻塞 | 长任务 |
| `DECISIONS.md` | 关键架构和兼容性决策 | 有重要决策时 |
| `HANDOFF.md` | 中断、压缩或 Agent 切换恢复快照 | 可能中断时 |
| `KNOWN_ISSUES.md` | 当前范围外已发现问题 | 按需 |
| `DELIVERY_RECORD.md` | 已形成实际交付的任务记录 | 产生交付时 |

已有职责相同的本机文档应优先复用，不重复创建同义文件。

---

## 四、与项目仓库严格隔离

外部记忆文档：

- 只能保存于 Agent 专用目录；
- 不得放入项目仓库；
- 不得加入暂存、提交和推送；
- 不得写入项目 CHANGELOG；
- 不得通过放入仓库再加入 `.gitignore` 规避隔离；
- 不得作为团队正式工程文档交付。

项目正式文档和外部记忆职责不同：

| 类型 | 保存位置 | 是否进入 Git | 作用 |
|---|---|---:|---|
| 项目 CHANGELOG | 项目仓库 | 是 | 正式功能和版本变更 |
| 架构、接口、部署文档 | 项目既有目录 | 按项目规范 | 团队工程文档 |
| Agent 外部记忆 | Agent 专用目录 | 否 | 恢复、计划、进度、复审和交接 |
| DELIVERY_RECORD | Agent 专用目录 | 否 | Agent 任务级交付记录 |

---

## 五、创建触发条件

出现以下任一情况时考虑建立外部记忆：

- 跨多个会话或多个工作日；
- 三个及以上实施阶段；
- 多模块、服务、仓库或工作树；
- 数据迁移、历史兼容或重大架构调整；
- 生产、灰度、回滚和观察期；
- 大量测试、六维复审、性能验证；
- 多 Agent 并行；
- 上下文接近压缩；
- 用户要求持续维护计划、进度或交付。

通常不需要完整体系：

- 单方法小修复；
- 简单说明、命令查询和静态分析；
- 不修改代码的简短问答；
- 纯提交拆分和提交信息修正。

---

## 六、更新时机

### 6.1 任务开始

确认或更新 PROJECT_CONTEXT、CURRENT_TASK 和必要的 PLAN，至少记录项目、目标、模式、范围、禁止项、验证、复审、验收、Git、推送、部署和重启授权。

### 6.2 有效阶段完成

更新 PROGRESS，记录实际完成、文件、类或配置、执行命令、构建、测试、复审、失败、未验证、阻塞和下一步。

不得只写“已完成”“已优化”“已验证”。

### 6.3 关键决策

更新 DECISIONS，记录背景、已确认事实、候选方案、选择原因、影响、兼容、性能、风险、回滚和重新评估条件。

### 6.4 独立复审

在 PROGRESS 或 DELIVERY_RECORD 中记录门禁类型、Reviewer、差异范围、六维结论、阻塞、重新验证和最终结论。不得把复审过程写入项目 CHANGELOG。

### 6.5 中断或上下文压缩

更新 HANDOFF，使新会话或 Agent 不依赖历史聊天即可恢复。

### 6.6 形成交付

更新 DELIVERY_RECORD，只记录实际形成交付的变更、验证、复审、Commit、推送、部署、重启和生效状态。

临时实验、格式调整和已回滚未交付尝试不写入正式交付记录。

---

## 七、恢复读取顺序

恢复任务时：

1. 当前用户消息和当前授权；
2. 平台和项目级指令；
3. PROJECT_CONTEXT；
4. CURRENT_TASK；
5. PLAN；
6. PROGRESS；
7. DECISIONS；
8. HANDOFF；
9. 实际 `git status`、`git diff`、分支和最近提交；
10. 项目正式文档和相关 CHANGELOG；
11. 重新阅读目标代码、配置和测试；
12. 对比文档与实际状态后继续。

不得仅根据 HANDOFF 或摘要直接修改代码。

---

## 八、事实冲突处理

外部文档与实际状态冲突时：

1. 明确冲突；
2. 以当前实际代码、配置、Git 和运行结果为准；
3. 重新验证；
4. 修正文档；
5. 记录冲突原因；
6. 不得因为文档写“已完成”而跳过验证和复审。

文档状态使用：已确认、高概率、推测、未验证、未开始、进行中、已完成、阻塞、已取消、已回滚、不适用。

---

## 九、文档内容和精简

优先保留：

- 目标、范围和授权；
- 已确认事实和关键决策；
- 修改文件和关键位置；
- 实际命令和验证证据；
- 复审和 CHANGELOG / Commit 对应；
- 当前问题、风险和下一步。

避免：

- 重复描述、完整对话和无关输出；
- 大段源码和终端日志；
- 内部推理；
- 失效猜测和主观结论；
- 密码、Token、密钥、隐私和企业敏感信息。

不要求每个微小步骤都更新全部文档，只在任务开始、有效阶段、关键决策、复审、交接和最终交付等节点更新。

---

## 十、多 Agent 协作

必须明确每个 Agent 的任务、可写目录、实施者、只读 Reviewer、分支或工作树、合并顺序、测试责任和最终集成人。

独立 Reviewer 不得与实施者共用同一可写上下文完成严格复审。

多个 Agent 不得无约束同时修改同一核心文件和共享进度文档。更新共享文档前重新读取最新内容，不覆盖他人记录。

记录 Agent 标识、角色、时间、模块、状态、依赖、交付和审查结论。

---

## 十一、归档

任务结束后：

- PROJECT_CONTEXT 保留长期有效事实；
- DECISIONS 保留有效决策；
- DELIVERY_RECORD 持续维护；
- CURRENT_TASK 切换或归档；
- PLAN、PROGRESS 和 HANDOFF 可归档到：

```text
<AGENT_CONTEXT_ROOT>/<项目标识>/archive/<任务标识>/
```

- KNOWN_ISSUES 已解决项更新状态，不静默删除；
- HANDOFF 标记任务结束，避免被误当成当前状态。

未经授权不得删除用户原有文档。

---

## 十二、文档维护不等于任务完成

以下不能单独证明任务完成：

- 更新 PROGRESS 或 DELIVERY_RECORD；
- 把计划改成已完成；
- 创建 HANDOFF；
- 文档宣称测试或复审通过；
- CHANGELOG 写明已修复。

完成仍以实际代码、构建、定向测试、复审、运行结果、Git 状态和验收证据为准。
