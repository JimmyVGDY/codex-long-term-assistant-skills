# 长期任务外部记忆、持续检查点与上下文恢复机制

> 仅在跨会话、多阶段、多模块、多仓库、多 Agent、生产风险、上下文可能压缩或用户明确要求持续跟踪时加载。简单一次性任务不得为了形式创建全部文档。

## 一、设计原则

### 1.1 外部记忆优先

对话上下文、模型内部记忆和压缩摘要只作为当前小节点的临时工作缓存，不作为长期任务状态的唯一来源。

长期任务的目标、授权、进度、证据、决策、阻塞和下一步必须持续写入本机外部记忆，使上下文压缩、会话中断、模型切换或 Agent 切换后仍能恢复。

### 1.2 最小丢失窗口

理想恢复边界：

> 上下文突然压缩或中断时，最多丢失当前尚未完成、尚未形成检查点的一个小节点；此前已经完成的节点必须已经持久化。

因此：

```text
MAX_UNPERSISTED_COMPLETED_NODES = 0
```

已完成的小节点不得只存在于当前对话中。

### 1.3 两类真相

#### 任务控制真相

由当前用户指令和外部记忆维护：

- 目标和非目标；
- 允许和禁止范围；
- 授权边界；
- 阶段和节点；
- 已完成、阻塞和下一步。

#### 技术事实真相

由实际状态决定：

- 当前代码和配置；
- Git 分支、HEAD、工作区和差异；
- 数据库、中间件和文件状态；
- 构建、测试、日志、监控和运行结果。

外部文档决定“计划如何继续”，不能覆盖“系统当前实际上是什么”。

### 1.4 内置 Memories 只是辅助

即使启用了 Codex Memories、Chronicle 或其他自动记忆，也不得将其作为任务硬规则、实时进度或交付证据的唯一来源。自动记忆可能延迟生成、遗漏活跃会话或只提供摘要；确定性的当前状态仍由本机制维护。

## 二、目录约定

根目录使用可配置占位符：

```text
<AGENT_CONTEXT_ROOT>/<项目标识>/
```

推荐结构：

```text
<AGENT_CONTEXT_ROOT>/<项目标识>/
├── PROJECT_CONTEXT.md
├── CURRENT_TASK.md
├── PLAN.md
├── PROGRESS.md
├── DECISIONS.md
├── HANDOFF.md
├── KNOWN_ISSUES.md
├── DELIVERY_RECORD.md
├── reviews/
│   └── <任务标识>/
│       ├── round-01/
│       ├── round-02/
│       └── round-03/
└── archive/
    └── <任务标识>/
```

`<AGENT_CONTEXT_ROOT>` 由当前机器、Codex Home、项目配置或用户明确指定，不在全局规则中写死用户名、Windows/WSL/Linux 路径或具体项目。

已有职责相同的本机文档应优先复用，不重复创建同义文件。

## 三、文档职责与写入模式

| 文档 | 作用 | 写入模式 | 更新触发 |
|---|---|---|---|
| `PROJECT_CONTEXT.md` | 长期稳定项目事实、技术栈和硬约束 | 低频修订 | 新的长期事实确认 |
| `CURRENT_TASK.md` | 当前任务最新快照 | 覆盖式 | 每个检查点 |
| `PLAN.md` | 阶段、依赖、风险、验证和复审计划 | 状态修订 | 计划变化、阶段变化 |
| `PROGRESS.md` | 按时间追加的检查点与证据索引 | 追加式 | 每个检查点 |
| `DECISIONS.md` | 重要架构、兼容和业务决策 | 追加式 | 关键决策 |
| `HANDOFF.md` | 暂停、压缩、切换后的最小恢复快照 | 覆盖式 | 交接或暂停 |
| `KNOWN_ISSUES.md` | 当前范围外问题 | 状态修订 | 发现或解决范围外问题 |
| `DELIVERY_RECORD.md` | 已形成实际交付的任务记录 | 追加式 | 形成交付 |
| `reviews/` | 子 Reviewer 原始结构化结果 | 独立文件 | 多 Agent 复审 |

### 3.1 热文档

每次恢复优先完整读取：

- `CURRENT_TASK.md`；
- `PLAN.md` 的当前阶段；
- `PROGRESS.md` 最近 3～5 个检查点。

### 3.2 温文档

按引用读取：

- `DECISIONS.md` 相关 ADR；
- `reviews/` 对应轮次报告；
- `KNOWN_ISSUES.md` 相关问题。

### 3.3 冷归档

当 `PROGRESS.md` 活跃检查点超过 30 条时，按任务和区间归档旧记录：

```text
archive/<任务标识>/PROGRESS-CP001-CP030.md
```

活跃 `PROGRESS.md` 只保留索引和最近检查点。不得每次恢复都重新加载完整历史。

## 四、启用条件与最小文档集

出现以下任一情况时启用：

- 跨多个会话或多个工作日；
- 三个及以上实施阶段；
- 多模块、服务、仓库或工作树；
- 数据迁移、历史兼容或重大架构调整；
- 生产、灰度、回滚和观察期；
- 大量测试、多 Agent 复审或性能验证；
- 当前上下文较长或预计会压缩；
- 用户明确要求每个节点持续记录；
- 中断后必须准确继续。

启用后最小文档集：

```text
CURRENT_TASK.md
PROGRESS.md
```

多步骤任务增加：

```text
PLAN.md
```

其余文档按事件创建，不机械创建全部模板。

通常不启用：

- 单方法小修复且当前会话可完成；
- 简单说明或一次性命令查询；
- 小范围静态分析；
- 无代码修改的简短问答；
- 纯提交拆分和提交信息修正。

用户明确要求持续检查点时，即使任务看似较小，也应遵循用户要求。

## 五、可独立恢复的小节点

### 5.1 定义

“小节点”是具有明确输入、操作、输出、证据和下一步，并可作为独立恢复位置的最小工作单元。

### 5.2 必须形成检查点的节点

- 完成一个模块、调用链或数据流的阅读并形成明确结论；
- 确认根因或排除一个重要候选原因；
- 完成一组同一功能边界的代码修改；
- 完成一次构建、定向测试、最小复现或导出样例验证；
- 完成数据库迁移或数据修复脚本的设计、执行或验证；
- 启动一轮多 Agent 复审；
- 收齐并归并一轮 Reviewer 结果；
- 形成最小完整修复集合；
- 完成一批集中修复；
- 形成关键技术或业务决策；
- 出现新的阻塞、失败、范围或授权变化；
- 创建提交、推送、部署、重启或完成环境验证；
- 准备等待用户确认、暂停或结束当前会话。

### 5.3 通常不单独形成检查点

- 单次 `ls`、`grep`、`find` 或查看一个短片段；
- 尚未形成结论的临时阅读；
- 修改一个标点或立即撤销的尝试；
- 无状态变化的重复检查；
- 子 Agent 的中间思考过程。

### 5.4 防止长时间无检查点

尚未完成一个完整小节点，但连续执行 5 个实质性动作时，必须写“进行中检查点”。

实质性动作包括：

- 修改代码或配置；
- 执行构建或测试；
- 运行会改变本地状态的脚本；
- 形成影响实现的结论；
- 派发或收集子 Agent；
- 处理数据库、缓存、消息、文件或环境；
- 改变计划、范围或授权判断。

```text
MAX_SUBSTANTIVE_ACTIONS_WITHOUT_CHECKPOINT = 5
```

## 六、检查点事务

每个检查点按以下顺序执行：

1. 重新读取 `CURRENT_TASK.md` 和 `PROGRESS.md` 尾部，避免覆盖其他更新；
2. 生成唯一检查点 ID，例如 `CP-20260729-001`；
3. 确认本节点实际完成内容和证据；
4. 先向 `PROGRESS.md` 追加检查点；
5. 再刷新 `CURRENT_TASK.md` 最新快照；
6. 验证两个文档的最后检查点 ID 一致；
7. 文档写入成功后再继续下一节点。

### 6.1 检查点内容

至少记录：

- 检查点 ID、时间和时区；
- 任务、阶段、节点类型和执行 Agent；
- 本节点目标；
- 实际完成内容；
- 已确认事实和证据等级；
- 修改文件和关键符号；
- 实际命令和结果摘要；
- 验证、复审和环境状态；
- 失败、阻塞、风险和未验证项；
- 对计划和范围的影响；
- 下一步唯一行动。

### 6.2 下一步必须可执行

禁止：

```text
继续优化
继续处理
继续测试
```

应写成：

```text
重新读取 OrderService.updateStatus() 及三个调用方，
确认新增幂等校验是否影响历史状态回写，并执行对应 Service 定向测试。
```

### 6.3 原子写入

工具允许时：

- 更新 `CURRENT_TASK.md` 使用临时文件后原子替换；
- `PROGRESS.md` 追加后刷新并确认写入；
- 写入失败不得假装检查点已完成。

可使用 `scripts/checkpoint.py` 辅助维护。脚本提供 `init`、`append`、`validate`、`recover`、`repair` 和 `archive`；共享写入时使用锁文件防止多个写入者并发覆盖，崩溃后只有确认不存在其他写入者时才允许清理遗留锁。脚本不可用时手工维护同等信息。

## 七、CURRENT_TASK 当前快照

`CURRENT_TASK.md` 必须保持短小、最新、可直接恢复，建议控制在 250 行以内。

至少包含：

- 状态版本；
- 最后检查点 ID 和更新时间；
- 项目、任务、分支、基线和当前 HEAD；
- 工作区差异摘要和未跟踪文件；
- 当前目标、非目标、范围和授权；
- 当前阶段和当前节点；
- 最近完成节点；
- 当前阻塞和未验证项；
- 多 Agent 复审轮次、深度和预算；
- 下一步唯一行动；
- 恢复前必须核对的实际状态。

不得把完整日志、长报告和历史流水堆入 `CURRENT_TASK.md`。

---

## 八、高风险操作的写前与写后检查点

适用：

- 生产写操作；
- 数据库 DDL / DML 和数据修复；
- Redis、MQ、对象存储和文件删除或迁移；
- Git 提交、推送、强制操作；
- 部署、重启、扩缩容和切流；
- 大范围自动改写；
- 多 Agent 复审启动；
- 任何不可逆或可能部分成功的操作。

### 8.1 操作前检查点

记录：

- 准备执行的动作；
- 目标环境、服务、实例、文件或数据范围；
- 当前状态和授权；
- 预计影响；
- 备份和回滚；
- 验收和停止条件；
- 操作尚未开始。

### 8.2 操作后检查点

记录：

- 实际执行的命令或动作；
- 成功、失败或部分成功；
- 实际影响范围；
- 是否回滚；
- 当前真实状态；
- 下一步验证。

如果上下文在操作中断，恢复 Agent 应能判断操作是未开始、进行中、部分完成、完成还是已回滚。

---

## 九、多 Agent 单一写入者机制

### 9.1 主协调 Agent

只有主协调 Agent 可以更新共享：

- `CURRENT_TASK.md`；
- `PLAN.md`；
- `PROGRESS.md`；
- `DECISIONS.md`；
- `HANDOFF.md`；
- `KNOWN_ISSUES.md`；
- `DELIVERY_RECORD.md`。

### 9.2 子 Agent

子 Agent：

- 只返回结构化结果；
- 或写入主协调 Agent 明确分配的独立文件，例如：

```text
reviews/TASK-XXX/round-01/security.md
```

- 不直接修改共享任务文档；
- 不覆盖其他 Agent 记录；
- 不把内部推理写入文档。

### 9.3 多 Agent 检查点

至少在以下时点持久化：

1. Reviewer 计划和预算确定；
2. Reviewer 已派发；
3. 所有结果收齐；
4. 结果归并和根因聚类完成；
5. 最小完整修复集合确定；
6. 集中修复完成；
7. 受影响验证完成；
8. 定向复核完成。

## 十、事件型文档更新

### 10.1 计划变化

更新 `PLAN.md`：

- 阶段增加、删除、阻塞或回滚；
- 依赖变化；
- 验证、复审、灰度或回滚方式变化；
- 用户调整目标或范围。

### 10.2 关键决策

更新 `DECISIONS.md`：

- 背景和已确认事实；
- 候选方案；
- 选择原因；
- 影响、兼容、性能和成本；
- 风险、防御和回滚；
- 重新评估条件。

### 10.3 范围外问题

更新 `KNOWN_ISSUES.md`，明确证据等级、影响和暂不处理原因，不擅自扩大任务。

### 10.4 交接或暂停

更新 `HANDOFF.md`，形成可让不了解历史聊天的新 Agent 恢复的最小完整快照。

### 10.5 形成实际交付

更新 `DELIVERY_RECORD.md`，记录实际交付、测试、复审、CHANGELOG、Commit、推送、部署、重启、生效和遗留风险。

临时实验、无行为变化格式调整和已回滚未交付尝试不进入正式交付记录。

## 十一、固定恢复协议

上下文压缩、会话恢复、模型切换、主 Agent 切换或长时间暂停后，不得直接继续修改。

按顺序执行：

1. 读取用户当前消息和当前授权；
2. 读取平台、全局和项目级 `AGENTS.md`；
3. 读取 `PROJECT_CONTEXT.md`；
4. 读取 `CURRENT_TASK.md`；
5. 读取 `PLAN.md` 当前阶段；
6. 读取 `PROGRESS.md` 最近 5 个检查点；
7. 按引用读取相关 `DECISIONS.md` 和 Reviewer 报告；
8. 必要时读取 `HANDOFF.md`；
9. 执行 `git status`；
10. 确认分支、HEAD、基线和未跟踪文件；
11. 检查 `git diff`、`git diff --stat` 和最近提交；
12. 对比文档状态与实际仓库状态；
13. 重新阅读“下一步唯一行动”涉及的核心代码、配置和测试；
14. 无冲突后才继续执行。

```text
RECENT_CHECKPOINTS_TO_LOAD = 5
```

不得只根据 `HANDOFF.md`、自动摘要、Codex Memories 或历史聊天结论直接修改代码。

## 十二、状态冲突处理

以下情况必须先停止和对账：

- 当前分支与文档不一致；
- HEAD Commit 不一致；
- Git diff 超出记录范围；
- 文件被其他 Agent 或用户修改；
- 文档写“测试通过”，但代码随后又变化；
- 计划中的下一步已被其他人完成；
- 授权边界、环境或数据目标不明确；
- 文档与运行状态冲突。

处理步骤：

1. 记录“状态分歧检查点”；
2. 明确冲突内容；
3. 以实际代码、配置、Git 和运行结果为准；
4. 重新验证受影响结论；
5. 修正文档；
6. 重新确定下一步。

旧测试结果在相关代码变化后自动失效，必须标记为“需重新验证”。

---

## 十三、与项目仓库严格隔离

外部记忆：

- 只能保存于 Agent 专用目录；
- 不得放入项目仓库；
- 不得加入暂存、提交和推送；
- 不得写入项目 CHANGELOG；
- 不得通过放入仓库再加 `.gitignore` 规避；
- 不得作为团队正式工程文档交付。

| 类型 | 保存位置 | 是否进入 Git | 作用 |
|---|---|---:|---|
| 项目 CHANGELOG | 项目仓库 | 是 | 正式功能和版本变更 |
| 架构、接口、部署文档 | 项目既有目录 | 按规范 | 团队工程文档 |
| Agent 外部记忆 | Agent 专用目录 | 否 | 恢复、计划、进度和复审 |
| DELIVERY_RECORD | Agent 专用目录 | 否 | Agent 任务级交付记录 |

提交前必须检查外部记忆未误入 Git。

---

## 十四、内容精简与安全

优先保留：

- 目标、范围和授权；
- 已确认事实和证据等级；
- 修改文件和关键符号；
- 实际命令和验证摘要；
- 复审、问题台账和决策；
- 当前阻塞、风险和下一步。

避免：

- 完整对话和内部推理；
- 大段源码、完整日志和无关工具输出；
- 重复描述；
- 失效猜测和主观结论；
- 密码、Token、密钥、Cookie、隐私和企业敏感信息。

文档中可引用日志、测试报告和 Reviewer 报告路径，不复制全部内容。

---

## 十五、归档

任务完成后：

- `PROJECT_CONTEXT.md` 保留长期有效事实；
- `DECISIONS.md` 保留有效决策；
- `DELIVERY_RECORD.md` 持续维护；
- `CURRENT_TASK.md` 清空、切换或归档；
- `PLAN.md`、`PROGRESS.md`、`HANDOFF.md` 和 `reviews/` 归档到：

```text
archive/<任务标识>/
```

- `KNOWN_ISSUES.md` 已解决项更新状态，不静默删除；
- `HANDOFF.md` 标记任务结束，避免误认为当前状态。

未经授权不得删除用户原有本机文档。

---

## 十六、文档维护不等于任务完成

以下不能单独证明任务完成：

- 更新 `CURRENT_TASK` 或 `PROGRESS`；
- 把计划改成已完成；
- 创建 `HANDOFF`；
- 文档宣称测试或复审通过；
- `CHANGELOG` 写明已修复；
- Codex Memories 中存在摘要。

完成仍以实际代码、构建、定向测试、复审、运行结果、Git 状态和验收证据为准。
