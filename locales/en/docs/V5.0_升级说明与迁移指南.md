# V5.0 Upgrade Notes and Migration Guide

## 1. Upgrade Goal

The V4.2 -> V5.0 upgrade retains the nine Skills, seven Reviewers, model tiers, Review Packet, Review Controller, and Checkpoint tool. It adds a lightweight governance runtime outside repositories to prevent four cross-project errors: project contamination, reused authorization, stale evidence, and overstated final status.

## 2. Compatibility

| Item | V4.2 -> V5.0 |
|---|---|
| Skill names | Unchanged |
| Reviewer TOML | Unchanged |
| `LIGHT/STANDARD/STRICT` | Unchanged |
| `economy/balanced/deep` | Unchanged |
| Four Luna/Terra tiers | Unchanged |
| `review_packet.py` / `review_controller.py` | Compatible |
| `checkpoint.py` | Compatible |
| `execution_guard.py` | Existing commands compatible; state migrates to schema 3 |
| Existing `config.toml` | Installer still does not modify automatically |
| Project repository | Governance state not written by default |

## 3. New Installed Content

```text
${CODEX_HOME}/
├── runtime/cp_runtime/       # V5.0 shared contracts and runtime
├── tools/cp-runtime.py       # Command entry
├── project-context/          # Created by project after first onboarding
├── skills/                   # Existing 9 Skills
├── agents/                   # Existing Reviewers
└── AGENTS.md                 # Merged managed rules
```

V5.0 uninstall does not delete `project-context/`, preventing loss of existing project memory and evidence. Deletion requires separate confirmation.

## 4. Recommended Upgrade

### 4.1 Validate the Package

```bash
python3 scripts/validate-package.py
```

### 4.2 Dry Run

```bash
./scripts/install-user.sh all --dry-run
```

Windows:

```powershell
powershell -ExecutionPolicy Bypass -File ".\scripts\install-user.ps1" -DryRun
```

### 4.3 Install and Verify

```bash
./scripts/install-user.sh all
./scripts/verify-user-install.sh
./scripts/doctor.sh
```

### 4.4 Continue Merging Codex Configuration

The installer does not edit `config.toml`. Continue merging `[agents]` according to `docs/CODEX_CONFIG_GUIDE.md` without overwriting existing settings.

## 5. First Project Onboarding

Run one bounded read-only onboarding for an actively maintained project:

```bash
python3 "$CODEX_HOME/tools/cp-runtime.py" project-onboard \
  --repo-path /path/to/repo \
  --project-id project-a
```

The tool reads Git and build markers near the repository root only. It does not access networks or production, run builds/tests, scan credentials, or label inferred entry points as confirmed.

After generation, check:

- `unknowns` in `project-profile.json`;
- build, test, and startup entries;
- environment, data sensitivity, and ownership;
- prohibited scan and modification paths.

## 6. V4.2 Task-State Migration

When V5.0 `execution_guard.py` first reads an old `execution-state.json`, it adds:

- `baseline_fingerprint`;
- `current_fingerprint`;
- `project`;
- `routing`;
- `authorized_actions`;
- `actions`.

Old tasks become `UNBOUND`; V5.0 never guesses a Project Profile. Create or reinitialize a project-bound envelope before protected operations.

## 7. Approval Migration

V4.2 booleans such as `authorization.create_commit=true` remain intent records but do not prove authorization still applies to the current project, task, environment, and baseline.

V5.0 protected-action flow:

```text
Explicit authorization obtained
  -> approval-issue
  -> authorize-action (validate and consume before action)
  -> external action
  -> record-action (read back after action)
  -> finalize
```

`approval-issue` cannot infer consent. Call it only after the upper session has explicit authorization.

## 8. Memory Migration

Existing `CURRENT_TASK.md`, `PROGRESS.md`, and checkpoints remain valid for task recovery but do not enter `project-memory.md` automatically.

Promotion:

```text
Checkpoint / Handoff
  -> memory-project
  -> human or controlled review
  -> memory-promote
  -> project-memory.md
  -> knowledge-candidate
  -> later cross-project review
```

## 9. Rollback

Restore the latest preinstall state:

```bash
./scripts/restore-latest-backup.sh
```

The restorer validates that the backup is under the managed backup root, the manifest is intact, every target is allowlisted for V5.0, content hashes match, and no backup path escapes its target.
