# v3.2 P0 优化设计说明

## 一、目标

v3.2 不继续增加领域 Skill 数量，而是提高现有体系的调度准确性、实施前风险发现、复审预算确定性、可观测性证据覆盖和外部记忆安全性。

P0 范围：

1. 最小充分 Skill 加载；
2. 高风险实施前设计与影响审查；
3. 多 Agent 复审状态控制器；
4. 日志 Skill 扩展 Metrics、Trace、Profiling、告警和变更事件；
5. 外部记忆权限、敏感信息和保留期治理；
6. Skill 路由回归测试集和观察工具。

## 二、最小充分加载

主 Agent 按当前阶段选择一个主领域 Skill，默认最多两个辅助 Skill。超过四个活动 Skill 时必须说明唯一职责。工作流采用延迟加载：只读分析不提前加载 Git、复审和长期记忆，只有进入对应阶段才激活。

该设计遵循“每条指令只出现一次、只暴露当前任务相关工具和规则、用代表性任务做回归”的原则，避免大型提示词和工具集稀释关键目标。

## 三、实施前和实施后双门禁

### 实施前

适用于公共契约、数据库迁移、权限、核心状态机、跨服务、高并发和生产迁移。默认一次、2～4 个 Reviewer，重点纠正高成本方向错误。

### 实施后

代码和最低验证稳定后，按现有六维执行 1～6 个 Reviewer，收齐结果后统一归因和集中修复。

两个门禁不能互相替代，全部 Reviewer 共同受单功能边界累计 12 个预算约束。

## 四、复审状态控制器

`review_controller.py` 不创建 Agent，不接触项目代码，只维护 JSON 台账并强制校验：

- pre / post 阶段；
- 轮次、深度、并行数和累计 Reviewer；
- 计划、派发、结果和归并；
- 集中修复轮次；
- 最终受控结论。

上下文压缩后先读取控制器状态，再决定是否允许下一轮，避免仅凭对话记忆突破上限。

## 五、多信号可观测性

统一证据模型包括：

- Logs；
- Metrics；
- Distributed Traces；
- Profiles / Dumps；
- Alerts；
- Deployments / Configuration Changes。

分析过程先统一范围和时间，再分别检查每类证据的采样、聚合和完整性，最后进行多源关联。任何单一信号的相关性都不能直接升级为根因。

## 六、外部记忆安全

- 最小必要信息；
- 常见明文凭据扫描；
- POSIX 目录 700、文件 600 建议；
- Windows ACL 人工确认；
- 默认完成任务 90 天、临时分析 30 天建议值；
- 保留期工具只报告候选，不自动删除；
- 不默认同步到云盘、NAS 或其他设备。

## 七、路由回归

路由测试分为两层：

1. 包内静态校验：测试用例格式、Skill 名称和规则一致；
2. 本机真实观察：在 Codex 中逐条运行 Prompt，记录实际激活 Skill，并使用工具评分 required、forbidden 和最大活动数量。

静态检查不能冒充真实自动激活验证。
