# v3.0 基础设计说明：持续外部记忆与多 Agent 独立复审

## 一、升级目标

v3.0 重点解决长期 Agent 任务中的两个系统性问题：

1. **复审发现不完整导致多次回炉**：单一 Reviewer 容易遗漏跨功能、兼容、安全、性能、数据和并发维度的问题，实施 Agent 往往需要多轮“发现一个、修一个、再发现一个”；
2. **上下文压缩导致任务状态丢失**：目标、授权、已完成节点、验证结果和下一步仅保存在对话上下文时，压缩、切换模型、会话中断或多 Agent 协作都会破坏连续性。

本版采用两条主线：

- **多 Agent 独立复审**：并行发现、统一归因、集中修复、定向复核；
- **持续外部检查点**：上下文作为短期缓存，确定性本机文档作为长期任务状态载体。

---

## 二、整体架构

```text
全局 AGENTS.md
    ├── 权限、真实性、最小改动和生产安全硬规则
    ├── 多 Agent 复审默认上限
    └── 持续检查点默认要求

按需 Skills
    ├── 技术域 Skills
    │   ├── Java
    │   ├── Python / AI
    │   ├── Vue
    │   └── 数据 / 中间件 / 基础设施
    ├── engineering-quality-delivery
    ├── multi-agent-independent-review
    ├── long-running-task-memory
    └── technical-document-writing

只读自定义 Reviewer
    ├── 功能与业务
    ├── 回归与兼容
    ├── 权限与安全
    ├── 性能与资源
    ├── 数据与契约
    ├── 状态与并发
    └── 测试与交付
```

`SKILL.md` 只保留触发条件、强制入口、关键参数和组合边界；详细规则放在 `references/`，模板放在 `assets/`，辅助工具放在 `scripts/`，避免每次任务把所有细则完整注入上下文。

## 三、多 Agent 复审设计

### 3.1 最少有效修复轮次原则

正式原则为：

> **一次发现、统一归因、集中修复、定向复核，追求最少有效修复轮次。**

“最少”不是强制一次完成，也不能成为忽略新问题的理由。它要求：

- 第一轮尽可能覆盖不同专业维度；
- 本轮 Reviewer 全部返回前不边审边零散修改；
- 主协调 Agent 去重并把同根因问题合并；
- 形成能够完整消除阻塞根因的最小修复集合；
- 集中修复后只复核受影响范围；
- 仍发现真实阻塞问题时继续处理，但不得无限循环。

### 3.2 Reviewer 不是越多越好

默认按风险选择：

| 风险 | 建议 Reviewer 数量 |
|---|---:|
| 低 | 1～2 |
| 中 | 3～4 |
| 高 | 5～6 |
| 关键 | 第一轮最多 6，按证据缺口定向追加 |

必须优先覆盖不同职责，禁止为了凑数量启动多个任务范围完全相同的 Reviewer。

### 3.3 中央协调、叶子只读

本包采用中央协调模型：

- 主协调 Agent 负责选择 Reviewer、维护预算、等待全部结果、归并和决定下一轮；
- 自定义 Reviewer 全部使用 `read-only`；
- Reviewer 不修改文件、不提交、不推送、不部署、不重启、不执行数据写操作；
- Reviewer 不自行派生其他 Agent，只能建议追加专项复审；
- 深度 2 或深度 3 的专项 Reviewer 仍由主协调 Agent 在预算内启动。

这比允许 Reviewer 自由递归更可控，也能避免递归树爆炸和重复审查。

### 3.4 硬限制

```text
MAX_REVIEW_AGENT_DEPTH = 3
MAX_REVIEW_ROUNDS = 3
MAX_PARALLEL_REVIEWERS = 6
MAX_TOTAL_REVIEW_AGENTS_PER_BOUNDARY = 12
MAX_REPAIR_ROUNDS = 3
```

含义：

- 深度 0：主协调；
- 深度 1：第一轮专业 Reviewer；
- 深度 2：冲突裁决、证据补足或专项第二意见；
- 深度 3：最终定向复核；
- 到达深度 3 后禁止继续自动派生；
- 同一功能边界最多 3 轮复审、3 轮集中修复；
- 同时最多 6 个 Reviewer；
- 所有轮次累计最多 12 个 Reviewer。

达到任一上限后停止自动循环，输出剩余阻塞、未验证项和用户决策点，不得为了结束流程伪称通过。

### 3.5 结果归并

主协调 Agent 必须形成统一台账，至少包含：

- 问题编号；
- Reviewer 和审查维度；
- 证据等级；
- 位置和触发条件；
- 影响范围；
- 是否由本次改动引入；
- 根因；
- 严重等级和是否阻塞；
- 同根因关联问题；
- 修复边界；
- 修复后验证方式。

多个表象属于同一根因时，必须合并为一个完整修复边界。例如消息重复消费、ACK 时机错误、唯一约束缺失和幂等记录缺失，应统一作为“消费幂等与成功边界不完整”处理，而不是分四次修改。

## 四、持续外部记忆设计

### 4.1 上下文不是长期状态库

正式原则为：

> 对话上下文只承载当前小节点的短期推理；已确认目标、授权、进度、证据、决策、阻塞和下一步持续写入外部任务文档。

理想恢复边界：

> 上下文突然压缩或中断时，最多丢失当前尚未完成的一个节点；此前已经完成的节点全部可从文档恢复。

因此：

```text
MAX_UNPERSISTED_COMPLETED_NODES = 0
```

### 4.2 可独立恢复的小节点

需要立即持久化的典型节点包括：

- 完成一个模块、调用链或数据流阅读并形成结论；
- 确认根因或排除重要候选原因；
- 完成同一功能边界的一组修改；
- 完成构建、测试、迁移、导出或最小复现；
- 派发、收齐或归并一轮 Reviewer；
- 形成最小完整修复集合；
- 完成集中修复或定向复核；
- 发生阻塞、失败、范围或授权变化；
- 创建提交、推送、部署、重启或完成环境验证；
- 准备暂停、等待用户确认或结束会话。

单次 `ls`、`grep`、尚未形成结论的阅读和立即撤销的尝试不单独形成检查点。

### 4.3 两个热文档

每个检查点至少更新：

1. `PROGRESS.md`：追加历史事实和证据；
2. `CURRENT_TASK.md`：覆盖为最新可恢复快照。

其他文档按事件更新：

| 事件 | 文档 |
|---|---|
| 计划或阶段变化 | `PLAN.md` |
| 长期稳定项目事实 | `PROJECT_CONTEXT.md` |
| 关键技术或业务决策 | `DECISIONS.md` |
| 范围外问题 | `KNOWN_ISSUES.md` |
| 暂停、压缩或 Agent 切换 | `HANDOFF.md` |
| 形成真实交付 | `DELIVERY_RECORD.md` |
| Reviewer 原始结果 | `reviews/<任务>/<轮次>/` |

### 4.4 检查点事务

每次检查点按以下顺序执行：

```text
重新读取共享文档最新状态
    ↓
生成唯一检查点 ID
    ↓
向 PROGRESS.md 追加记录
    ↓
刷新 CURRENT_TASK.md 最新快照
    ↓
校验两者最后检查点 ID 和状态版本一致
    ↓
继续下一节点
```

若 `PROGRESS.md` 已追加但 `CURRENT_TASK.md` 刷新失败，可使用 `checkpoint.py repair` 根据最后检查点修复当前快照。

### 4.5 防止长时间不落盘

即使尚未完成完整节点，连续最多 5 个实质性动作必须写入“进行中检查点”：

```text
MAX_SUBSTANTIVE_ACTIONS_WITHOUT_CHECKPOINT = 5
```

### 4.6 高风险操作双检查点

高风险、不可逆或可能部分成功的操作必须：

- 操作前记录目标、授权、影响、备份、回滚、停止条件和“尚未开始”；
- 操作后记录实际命令、成功/失败/部分成功、实际影响、回滚和下一步验证。

即使上下文在操作中断，恢复 Agent 也能判断真实状态。

### 4.7 单一记忆写入者

```text
SINGLE_MEMORY_WRITER = true
```

- 只有主协调 Agent 写共享任务文档；
- 子 Agent 返回结构化结果，或写主协调 Agent 明确分配的独立 Reviewer 报告；
- 共享写入前重新读取最新内容；
- `checkpoint.py` 使用锁文件和原子替换降低并发覆盖和半写入风险。

### 4.8 冷热分层

默认：

```text
RECENT_CHECKPOINTS_TO_LOAD = 5
HOT_PROGRESS_CHECKPOINT_LIMIT = 30
```

- 恢复时完整读取当前快照和最近 5 个检查点；
- 活跃 `PROGRESS.md` 最多保留 30 个检查点；
- 更早记录归档到 `archive/`，热文档只保留索引；
- 不要求每次恢复加载完整历史。

## 五、恢复协议

上下文压缩、会话恢复或 Agent 切换后，必须：

1. 读取用户当前消息和当前授权；
2. 读取全局及项目级 `AGENTS.md`；
3. 读取 `PROJECT_CONTEXT.md`、`CURRENT_TASK.md` 和 `PLAN.md` 当前阶段；
4. 读取 `PROGRESS.md` 最近 3～5 个检查点；
5. 按引用读取相关决策和 Reviewer 报告；
6. 检查 Git 分支、HEAD、工作区、未跟踪文件和差异；
7. 核对代码、配置和验证证据；
8. 对比文档状态与实际状态；
9. 重新阅读下一步涉及的核心代码；
10. 一致后才能继续执行。

出现分支、HEAD、差异、授权或环境冲突时，应先停止并记录“状态分歧检查点”，不得直接沿用旧结论。

## 六、组合执行流程

```text
恢复外部记忆并核对仓库
    ↓
执行一个可恢复小节点
    ↓
追加 PROGRESS + 刷新 CURRENT_TASK
    ↓
完成功能边界修改
    ↓
执行最低定向验证
    ↓
写入复审启动检查点
    ↓
并行只读 Reviewer
    ↓
等待全部返回并统一归因
    ↓
写入归并检查点
    ↓
集中修复最小完整修复集合
    ↓
重跑受影响验证
    ↓
定向复核受影响维度
    ↓
更新 CHANGELOG、交付记录和 Commit
```

这套机制确保代码质量门禁和任务连续性相互配合：复审负责尽量一次找全问题，外部记忆负责保证任何节点都能在上下文压缩后准确继续。

---

## 七、明确边界

- 多 Agent 复审不能替代构建、测试、数据库验证或生产验收；
- 外部文档不能覆盖当前代码、配置、Git 和运行事实；
- 文档中“已完成”不能证明实际完成；
- Reviewer 不能借复审获得写权限；
- 不能为了减少修复轮次扩大到无关重构；
- 不能为了达到 Reviewer 数量而重复审查；
- 达到上限后必须停止自动循环并如实报告；
- 外部任务文档不得进入项目仓库、Git 或项目 `CHANGELOG`。
